# Проверка браузера UgPhone

Страница: https://demochko.com/hosting-webrtc-probe/phone-exit-browser-test/

Это отдельный диагностический канал, не VPN и не прокси. Native peer на ПК
использует тот же адаптер node-datachannel, что продукт. На телефоне отвечает
WebRTC браузера. Только UDP IPv4 кандидаты, без TURN, камеры и микрофона.
Успех — пять последовательных ping/pong и doneAck по DTLS/SCTP. Отчёт браузера
сам по себе не считается подтверждением. Успех не доказывает TCP/UDP/DNS VPN,
WAN, работу игр или длительную стабильность.

## Запуск

Из корня проекта:

```powershell
node.exe --use-system-ca phone-exit/pc/scripts/browser-direct-probe.mjs phone-exit/.tools/browser-direct-session
```

Ссылка сохраняется в `phone-exit/.tools/browser-direct-session/link.txt`.
Скопировать её в Chrome **на UgPhone**, нажать «Начать проверку» и оставить
страницу открытой до результата. На ПК не открывать эту пользовательскую
тестовую ссылку: это проверит другой исходящий узел. Для следующего прогона
создать новую сессию, обновить страницу телефона и открыть новую ссылку.

Комната получает 256 случайных бит, не использует account.bin / привязки.
Ключ в URL fragment, не в query: fragment не передаётся HTTP-серверу и удаляется
из URL страницы после выполнения модуля. Ключи и SDP не печатаются программой.
Ссылка и результаты остаются вне Git. Ссылку не публиковать и не передавать
посторонним. ПК ждёт максимум 10 минут; после ответа браузера максимум 90 с.
После результата / ошибки peer, канал и таймеры закрываются, повтор не запускается.
PID и время окончания записаны в приватный session.json; процесс принадлежит
запустившей его exec-сессии. Node завершается после cleanup. Кнопка Stop и
pagehide закрывают peer телефона. Новый APK не нужен.

## Сигнализация и границы

Используется существующий `../signal.php`, без изменений его кода/данных.
Отдельная случайная комната, роли pc/phone: offer/answer/candidate. Финальный
candidate с value=null дополнен probeReport — только разрешённые счётчики и
исход. Это end-of-candidates с диагностическими метаданными, не команда продукту.
SDP ≤ 11000 символов, до 32 trickle-кандидатов на сторону, кандидат ≤ 2048,
до 32 пар в отчёте; кадры DataChannel ≤ 256 символов, очередь ≤ 4096 байт.
Серверные ограничения комнат/TTL сохраняются. HTTPS хранит служебные SDP/ICE
в существующем временном хранилище сигнализации вне веб-каталога; пользовательский
трафик туда не отправляется. Вывод содержит только состояния и разрешённые
счётчики RTCStats. Отсутствующие поля не заменяются нулями.

FTPS-публикация: `server/publish-browser-probe.py`, credentials только stdin.
Только отдельный каталог phone-exit-browser-test, с проверкой owner.txt;
существующие signal.php / control.php / APK / сайт не меняются. Проверяются
FTPS hash и HTTPS JS bytes / заголовки HTML. JS отдаётся с расширением .js:
на этом хостинге .mjs отдаётся как application/octet-stream и не исполняется.

## Проверено 22 октября 2026

3 Node-теста: IPv4-фильтрация и редактирование отчёта, настоящий native WebRTC
с пятью echo, cleanup и отклонение ложного отчёта connected без подтверждений.
PHP lint и JS syntax check прошли. Полный локальный прогон опубликованной
страницы в Chromium in-app browser → native PC прошёл за 2064 мс, 5 pong /
doneAck, получен безопасный отчёт. Это одна локальная сеть, не удалённый UgPhone.
Удалённый прогон Chrome на UgPhone: пользователь запустил страницу, ПК получил
answer по HTTPS, но DataChannel не открылся. Совпадающие пользовательский экран
и полученный ПК probeReport: failed, 0 ping/pong, elapsedMs=15954; в последнем
снимке 3 пары по requestsSent=80, requestsReceived/responsesReceived=0,
nominated=false. Пустые байтовые счётчики не являются захватом пакетов на проводе.
ПК сохранил безопасный result.json и завершил собственный процесс / peer.
Отказ воспроизвёлся и в Chrome, и в APK, поэтому он не ограничен кодом APK.
Это ещё не доказательство конкретной блокировки провайдером: маршрут / NAT /
фильтрация пары сетей остаются возможными причинами. HTTPS-сигнализация в этом
прогоне работала; общая причина с предыдущим сбоем загрузки APK не установлена.

Опция CLI `--qa-redirect` только для локального UI-теста создаёт одноразовый
loopback HTTP redirect на случайную ссылку, автоматически закрывается после
первого GET либо завершения процесса; по умолчанию listener отсутствует.
