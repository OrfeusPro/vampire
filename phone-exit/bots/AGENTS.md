# Игровые модули Phone Exit

Этот файл дополняет корневой `AGENTS.md` для всех модулей и инструментов в `bots/`.
При изменении игрового интерфейса в `pc/` также применять эти правила.
Состояние и API модулей — в [README](README.md), состояние конкретной игры —
в её главном README. Историю результатов не добавлять в AGENTS.md.

## Сначала источники и связи

- Перед реализацией сценария, распознавания, кнопки, попапа или карты искать
  элемент в данных установленной игры и уже извлечённых связях.
- Проверять цепочку: условие / задание → действие → текстовый ключ → ресурс окна
  → контрол / дочерний виджет → размеры, отступы, anchors, alignment и контейнеры.
  Для покупки / награды также проверять товар, валюту, количество, стоимость,
  ограничения и результат.
- Фиксировать происхождение: путь, версию и SHA256 источника, строку таблицы /
  экспорт / смещение, связанные ID и воспроизводимый инструмент извлечения.
- Затем сверять с актуальным экраном: DPI, разрешение, масштаб, смещения,
  видимость, анимация и серверное состояние. Имя и размер контрола сами по себе
  не доказывают координату клика.
- Неизвестное записывать явно. Временное визуальное решение допускается с
  указанными границами и проверкой результата, без слепого повторения действий
  с необратимым эффектом. Общие попапы связывать с повторно используемыми controls.
- Собранный EXE и cooked-ресурсы называть кодом / данными клиента;
  не выдавать их за доступный исходный C++ проект.

## Геометрия интерфейса как в игре

- Автосборщик Vampir сначала сканирует характеристики и связи в версионированную
  вложенную структуру с прямыми / обратными индексами, затем проходит каждую
  характеристику по источнику, чтению, наследованию, применению и проверке.
  Проверенные правила подключать к сборке по мере готовности, не ожидая закрытия
  независимых характеристик всего каталога. Для допуска фиксировать SHA источников,
  версию правила, зависимости, результаты и границы проверки; кандидатные сведения
  не применять как подтверждённые. Аудит остальных свойств продолжается. Текущую фазу вести
  в UI-GENERATION-GATE.json. Перечень требуемых свойств и автоматически найденные
  поля различать; сканирование старого декодированного каталога не доказывает
  полноту UProperties, активных настроек, dynamic bindings и native handlers.

- Интерфейс Vampir развивать через единый автоматический сборщик: извлечённые
  данные → схема и граф зависимостей → общие правила контейнеров / компонентов /
  оформления / событий → локальный интерфейс. Новое подтверждённое правило
  добавлять в сборщик и применять ко всем подходящим потребителям. Прототип —
  проверочный результат этого процесса. Ручные исключения хранить отдельно с
  причиной, источником и SHA. Сборка не должна угадывать активный вариант,
  неизвестные bindings, DPI или поведение по именам; пробелы выводить в отчёт.

- Повторяющиеся части интерфейса собирать из подключаемых компонентов: портрет /
  HP / MP, валюты, меню, заголовок / возврат / закрытие, кнопки, слоты и общие
  попапы. Не копировать их разметку, данные и обработчики по окнам. Для компонента
  фиксировать исходный WBP / вариант / SHA, состав, точки подключения и параметры;
  для каждого использующего окна — свою цепочку размещения и проверки.
  Данные передавать из общей модели, действия — через отдельный адаптер;
  отображаемое состояние, внешний вид и событие не смешивать с транспортом.
  Исправление общего компонента применять ко всем потребителям и перепроверять
  их. Для 50 окон исключать дубли подписок, фоновых таймеров и загрузки общих
  ресурсов; при скрытии / закрытии освобождать принадлежащие компоненту ресурсы.

- Для каждого игрового окна, попапа и дочернего контрола обязателен собственный
  паспорт геометрии и отдельный пункт проверки: ресурс / вариант / полный SHA,
  корень, цепочка родителей и слотов, входные размеры и масштабы, результат и
  оставшиеся неизвестные. Готовую геометрию брать из извлечённой структуры клиента;
  скриншот использовать для сверки. Наличие профиля с ручным прямоугольником
  не означает восстановление расположения. Уже реализованные окна обязательно
  повторно проверять по этому правилу; работоспособность проверять отдельно.

- Общие элементы (валюты, иконки, кнопки и их состояния, рамки, слоты, вкладки)
  вести в повторно используемом реестре с ID, полным путём и SHA256 источника.
  Использовать извлечённые оригиналы; одинаковые картинки / названия не объединяют
  разные типы валют. Normal, pressed, selected, hover и disabled различать;
  соответствие по имени текстуры считать кандидатом до проверки brush binding.
  Неизвестные состояния и временное CSS-оформление отмечать явно. Обновление
  общего элемента должно создавать проверки для всех использующих его окон.

- Для оформления обязателен такой же отдельный паспорт и повторный проход
  каждого окна, как для геометрии, включая уже реализованные окна. Фиксировать
  связь контрол → дочерний Image / Brush / Style → полный путь ресурса и SHA;
  размер и положение иконки, normal / hover / pressed / selected / focused /
  disabled, рамки / nine-slice, цвет / оттенок, прозрачность, шрифт, обводку,
  тени, эффекты и анимации. Учитывать наследование, dynamic bindings и material
  parameters; отличать LinearColor / sRGB, tint, ColorAndOpacity и RenderOpacity
  родителя / ребёнка, не применять одно преобразование или alpha дважды.
  Совпадение имён и наличие текстуры в пакете не доказывают brush binding.
  Неизвестные свойства и временный CSS отмечать явно. Отсутствующие иконки,
  оформление и состояния заносить в чеклист повторной проверки; работа кнопки
  и наличие PNG не закрывают визуальную проверку окна.

- В паспорте контрола раздельно учитывать исходные delegates / callbacks
  (pressed, released, clicked, hovered, focus, changed / selected), визуальное
  состояние, доступность действия и подтверждённый результат. Наличие имени
  обработчика не доказывает его привязку или серверное выполнение. Фиксировать
  binding, условия / порядок событий, отмену и потерю фокуса / окна / соединения,
  повтор, disabled / loading и подтверждение результата. Демо-события обозначать
  отдельно; подключение реального бота не опережать готовностью визуального слоя.
  Для найденного события сохранять цепочку контрол → binding → handler → callees
  → изменение состояния / запрос → результат: имя / ID функции, аргументы,
  условия, экспорт / адрес и полный SHA клиента, границы доказательства и unknowns.
  После обновления клиента перепроверять привязку и цель; имя виджета и события
  сами по себе не определяют контракт действия будущего адаптера бота.

- Для каждого окна и дочернего контрола рассчитывать собственное размещение по
  подтверждённой иерархии игры: viewport / родительский контейнер → anchors →
  offsets / margins → alignment / pivot, padding, AutoSize / desired size и
  ограничения SizeBox / ScaleBox. Учитывать SafeZone, RenderTransform и ZOrder,
  если они участвуют в цепочке. Локальные координаты не считать экранными.
- Явно различать физические пиксели, логические единицы интерфейса и масштаб
  браузера / WebView. Учитывать DPI окна, viewport, ApplicationScale и выбранный
  UI Scale игры; не применять один коэффициент повторно на нескольких уровнях.
  Пресет масштаба или значение по умолчанию не доказывает активный масштаб игры.
- При смене разрешения, размера окна, DPI монитора, UI Scale, содержимого,
  влияющего на desired size, или версии ресурса пересчитывать затронутую геометрию.
  Области клика, подсказки, вложенные попапы и отрисовка должны использовать
  одну цепочку преобразований. Системные настройки DPI для проверки не менять.
- Проценты и координаты, измеренные по скриншоту, допускаются только как явно
  обозначенное временное приближение. Общий шаблон попапа не заменяет собственную
  геометрию окна. При неизвестном DPI, архетипе, desired size или родителе отмечать
  пробел и задачу проверки; не объявлять точное совпадение с игрой.
- Хранить происхождение расчёта: версия / полный SHA256 источника, ресурс,
  exports / slots, входные размеры и масштабы, известные ограничения. Сверять
  результат с кадрами игры при сопоставимых условиях, включая края, размеры,
  переносы текста, обрезку, прокрутку, вложенность и фактические области клика.
- Для множества окон кэшировать подтверждённые схемы и пересчитывать размещение
  по изменению входов; не выполнять полный обход геометрии каждого бота каждый
  кадр. Экономия ресурсов не должна менять правильное размещение активного окна.

## Vampir: порядок исследования

Сначала читать [главный README Vampir](vampir/README.md), затем
[TASKS](vampir-headless/TASKS.md), соответствующий вопрос в
[questions.json](resource-tools/vampir/knowledge/questions.json) и его evidence.
Правила структуры знаний — в [knowledge/README](resource-tools/vampir/knowledge/README.md).

1. Начинать новое исследование через `knowledge-index.py prepare` с question ID,
   явными адресами и `--release installed`. Команды запускать из корня репозитория;
   инструмент находится в `phone-exit/bots/resource-tools/vampir/`.
2. Использовать найденные материалы. Для дополнительного поиска — `function`,
   `search`, `callers` с явной версией. Отсутствующий индекс / новые выгрузки
   обрабатывать через `build`; `prepare` делает это сам.
3. Недостающий явный набор получать через `collect --request <manifest>`.
   Не расширять анализ на весь EXE. Повтор разобранной ветви допустим только
   при изменении входов или для конкретного записанного unknown / decision_rule.
4. Завершать через `finish --request <manifest> --result <JSON>`: вывод, метод,
   границы fixtures, оставшееся неизвестное, следующая проверка и evidence.
   Обновлять смысловые README / вопрос по фактическому результату.
5. Перед коммитом выполнять `knowledge-index.py check` и
   `git diff --cached --check`. Проверять русский текст и смысл чисел по diff;
   не делать массовую замену слов / цифр в технических обозначениях.

[Формат и команды workflow](resource-tools/vampir/knowledge/RESEARCH-WORKFLOW.md).
`function-registry.py --query` сохраняется для прежних ролей / evidence;
исторический реестр требует явного `--source-snapshot` того же SHA.
После изменения его входов перестраивать через `--build` в том же режиме.
Не отключать проверку SHA и не подставлять старый адрес при отсутствии новой версии.
Аналитическое имя, упоминание адреса и полный экспорт не доказывают роль;
bounded replay с fixtures не доказывает целую сессию. Новые выводы сохраняются
по полному SHA в `knowledge/releases/<SHA>/facts.json`; старые не переносить автоматически.

## Выбор инструментов и обновления

Сначала читать [ANALYSIS-TOOLS](resource-tools/vampir/ANALYSIS-TOOLS.md) и готовые
результаты; закреплённые версии и команды брать оттуда.

- Native EXE / DLL: Ghidra. Перед новым экспортом использовать общий индекс
  и `F:/PhoneExit Resources/Vampir/ghidra/INDEX.md`, учитывая SHA этого указателя.
  Псевдокод и угаданные типы сверять с инструкциями; поведение проверять целыми
  ограниченными native-сценариями, где возможно.
- При поиске переместившихся функций использовать готовое сравнение BinExport /
  BinDiff по двум полным SHA, если оно есть. Совпадения остаются кандидатами:
  проверять границы, callees, данные и связанные checks до подтверждения роли.
  [Порядок и команды](resource-tools/vampir/knowledge/evidence/tools/HEADLESS-BINARY-DIFF.md).
  Полный экспорт большой базы не делать обязательным этапом каждого обновления.
- Unreal PAK / UAsset: проверять CUE4Parse и существующие извлечения. Зашифрованный
  индекс без подходящего ключа не считается разобранным; чтение заголовка не
  доказывает чтение всех UObject properties. Не повторять неудачный путь без новых входов.
- Dumper-7: для reflection / SDK / mappings работающего клиента. Совместимость
  с Vampir не следует из успешной сборки DLL. Внедрение в игру требует отдельного
  явно согласованного эксперимента; установка инструмента его не разрешает.
- Capstone / Unicorn и собственные декодеры: для проверки инструкций, ограниченных
  сценариев и доказанных нестандартных форматов. Готовый parser не переписывать
  без установленной причины.

Исследовательские инструменты не включать в лёгкий runtime. SDK, EXE / PAK,
большие экспорты и поисковую SQLite базу хранить вне Git в библиотеке ресурсов;
версии, SHA, команды и небольшие записи знаний — в репозитории.

Обычное обновление игры — по средам рано утром, точное время не установлено.
После окончания загрузки использовать `knowledge-index.py update` с явным baseline:
сверить SHA, переизвлечь изменённые доступные данные и перепроверить затронутые связи.
Совпадение samples не равно полному SHA. Неоднозначности оставлять в очереди;
runtime profile и совместимость не объявлять обновлёнными автоматически.
При подтверждении функции отмечать в `knowledge/release-update-targets.json`
возможность автоматизации: полный SHA, адрес, границы проверки, required_checks,
способ поиска и то, что требует ручной сверки новой сборки. Разделять поиск
кандидата, автоматическую проверку и разрешение обновить runtime; совпадение
строки или адреса не подтверждает все три этапа.
Фоновое расписание без отдельного запроса не создавать.
