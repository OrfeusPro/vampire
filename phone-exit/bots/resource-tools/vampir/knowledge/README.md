# База знаний Vampir: порядок исследования

Главный вход остаётся [README бота](../../../vampir/README.md).
Здесь хранится **текущее знание**, а не ещё один хронологический журнал.
База не означает, что весь EXE разобран: сейчас индексируются функции
последнего проверенного Ghidra export и ссылки на существующие исследования.
Адреса из документов вне экспорта тоже доступны поиску, но помечены отдельно:
это могут быть данные, callsites или ещё не экспортированные функции.
Генератор не объявляет любой найденный адрес функцией.

## Разделение записей

| Что нужно найти | Где хранится | Как обновляется |
| --- | --- | --- |
| Цель, текущий результат, путь запуска | README бота / TASKS | Кратко, по проверенным изменениям |
| Открытый вопрос, что известно, что проверять дальше | [questions.json](questions.json) | Одна запись на вопрос с постоянным ID |
| Установленная роль функции и её границы | [function-roles.json](function-roles.json) | По VA и SHA клиента; только проверенные утверждения |
| Все выбранные функции, входящие/исходящие calls, ссылки на разборы | `F:/PhoneExit Resources/Vampir/knowledge/function-registry.json` | Генерируется `function-registry.py --build`, вручную не редактируется |
| Псевдокод и source-bound диапазоны | `F:/PhoneExit Resources/Vampir/ghidra/` | Существующие manifest / immutable export / verifier |
| Подробный разбор, native fixtures, тесты, границы вывода | `HEADLESS-*.md`, scripts / tests | Существующие пути сохраняются; уточнения явно ссылаются на продолжение |
| Сырые выгрузки, большие отчёты, tools, SDK | `F:/PhoneExit Resources/Vampir/` | Вне Git; SHA и команды в подробном разборе |

Legacy-документы не перемещаются массово: пути используются кодом, тестами и
ссылками. Новые тематические подразделы создавать по необходимости, а не по
одному каталогу на каждый небольшой шаг. При переносе сначала проверить и
обновить все ссылки и зависимости; хранить одну авторитетную копию результата.
Секреты, credentials, профили и реальные device keys в базе не хранить.

## Перед следующим исследованием

1. Прочитать README и соответствующий вопрос в questions.json. Если вопрос
   уже имеет bounded_answer, сначала проверить, покрывает ли результат новую задачу.
2. По адресу и имени найти функцию в реестре. Адреса с `0x` и без него равнозначны.
3. Прочитать established_role и limits, затем evidence и найденные references.
   Простое упоминание адреса не подтверждает роль; аналитическое имя — тоже.
4. Сверить SHA клиента, готовый экспорт и границы прежних fixtures. Если нужная
   ветвь уже выполнена, использовать её результат. Новая работа должна отвечать
   на конкретное unknown или проверять изменившийся вход, а не повторять результат.
5. Выбрать следующую функцию/ветвь и записать, какой вывод изменит проверка.
   Ghidra — до ручного instruction replay; готовые индексы — до нового scanner.
   Для каждого вопроса decision_rule ограничивает следующий эксперимент:
   не наращивать покрытие вспомогательного кода без связи с текущей целью.

Пример из корня репозитория:

```powershell
python -X utf8 phone-exit/bots/resource-tools/vampir/function-registry.py --build
python -X utf8 phone-exit/bots/resource-tools/vampir/function-registry.py --query 14453cdf0
python -X utf8 phone-exit/bots/resource-tools/vampir/function-registry.py --query SendSignIn
python -X utf8 phone-exit/bots/resource-tools/vampir/function-registry.py --question common-data-population
```

## Как оценивать доказательства

- `diagnostic_and_static`: compiled literal и проверенные ссылки / инструкции.
- `bounded_native`: native-исполнение конкретной ветви с описанными fixtures.
- `diagnostic_and_bounded_native`: оба вида, с теми же ограничениями.
- Отсутствие curated role не означает, что функция неизвестна: сначала читать
  собранные ссылки. Роли переносятся в curated записи после сверки доказательств.
- `open` у вопроса — нет достаточного ответа. `bounded_answer` — дан ответ в
  указанных границах. `blocked_experiment` — конкретный эксперимент остановлен,
  а не весь проект. Статусы вопросов не заменяют состояние задачи / goal.

Не повышать доказательство: decompilation не равна успешному runtime;
fixture не равен наблюдению живого аккаунта; успешный SDK не равен игровому Login;
одинаковый код ошибки не доказывает причину. Опровергнутый кандидат сохраняется
в known / do_not_repeat, чтобы его не предлагать снова как новую находку.

## После результата

Обновить подробный разбор, соответствующий вопрос и curated role, если её
семантика установлена. В README/TASKS достаточно краткого состояния со ссылкой.
Затем построить реестр и выполнить подходящие проверки. Генератор проверяет
SHA источника, manifest/export, псевдокод, существование evidence и ссылки
вопросов. Query отказывает при изменении входных документов / конфигурации:
устаревшую базу нельзя молча использовать как текущую.

Коммит должен фиксировать один понятный результат или изменение структуры.
Подробные логи команд и каждое ожидание отдельно в README не добавлять.
После обновления игры прежние VA и выводы считать историческими до проверки
SHA и затронутых связей; не переносить их автоматически в новый реестр.
