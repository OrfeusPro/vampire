# План быстрого обновления Vampir

Текущий интерфейс, журнал и ограничения описаны в [RESUMABLE-UPDATE](RESUMABLE-UPDATE.md).

Цель: после патча повторно разбирать только изменённые данные и затронутые связи.
Полный перенос, который выполняется сейчас впервые, не должен становиться
обязательной работой после каждого патча. Время полного обновления пока не
измерено на следующей реальной сборке; обещать завершение за фиксированное
число минут без этого нельзя.

## Рабочая цепочка

| Этап | Что уже автоматизировано | Что требует доработки |
| --- | --- | --- |
| Загрузка завершена | Явный запуск update; inventory / стабильность / полные SHA | Сигнал завершения лаунчера пока подтверждает пользователь |
| Изменения ресурсов | Только изменённые доступные PAK, configs / records / tables через adapters | Семантические связи без check и отсутствие подходящего baseline остаются в queue |
| Проверки | Явные on_update checks, кэш по source / dependency SHA, ошибки и requires_port в queue | Добавлять покрытие всех нужных runtime связей; сейчас покрытие частичное |
| Поиск кода | Точные ориентиры, prefix с проверкой объявленных связей, явные constructor / vtable / direct call | Для неописанных связей и новых SHA без подходящей проверки остаётся ручная очередь |
| Экспорт | Контроллер собирает недостающие явные roots пакетами до 32; готовые exports переиспользуются | Проверять новые границы и неоднозначные адреса, не расширять дерево вызовов автоматически |
| База знаний | Добавление новых exports без повторного импорта прежних, атомарная замена | Измерять дальнейшие узкие места; полный SHA guard сохраняется |
| Runtime profile | Общий сборщик выбирает reports по контексту SHA, сверяет зависимости и сохраняет отдельный prepared profile | Полный игровой профиль, продвижение и живой вход требуют отдельных проверок |

Посторонняя правка документа не должна запускать native replay, если документ
не объявлен входом проверки. Совпадение текста функции с замаскированными CALL
не доказывает неизменность вызванного кода. При новом SHA нужно подтвердить
адреса, данные, callees и границы; старые факты не копировать как новые.

## Порядок следующего патча

1. После загрузки вызвать `knowledge-index.py update --baseline <manifest>`.
   Использовать явный последний проверенный baseline; не повторять полный аудит
   для каждого следующего исследовательского вопроса того же патча.
2. Читать сохранённые comparison / checks / native_targets / queue. При тех же
   входах переиспользовать отчёты. Проверка без поддержки нового SHA означает
   конкретную задачу переноса, а не повтор всей старой истории.
3. Из подтверждённых ориентиров собрать явные адреса для одного `prepare`
   вопроса обновления и одного `collect`, до 32 roots. Готовые функции не
   выгружать повторно. Не расширять дерево вызовов автоматически.
4. Для изменения поведения получать только недостающие callees / данные,
   указанные в причине следующего эксперимента. Запускать связанные проверки;
   ошибки и неоднозначности оставлять в очереди с причиной и следующим шагом.
5. Собирать профиль из подтверждённых текущих reports; сохранять flags области
   проверки. Отдельно проверять один реальный вход, когда серверы доступны.
   Только после этого фиксировать применимость runtime.

## Ближайшая автоматизация по приоритету

1. Закончить source checks Version / Login / character selection / world
   completion текущего патча. Их новые адреса и зависимости сразу сохранять в
   машинный план, чтобы следующий перенос начинался с готовых ориентиров.
2. Разделить зависимости native доказательства и служебного workflow там,
   где изменение orchestration не меняет проверяемое поведение. Каждое такое
   выделение само требует сверки: нельзя просто удалить dependency ради кэша.
3. Расширять объявленные способы получения привязок. Контроллер уже собирает
   явные адреса в пакеты, но неизвестные связи и неоднозначные адреса требуют
   отдельной проверки перед подтверждением.
4. Довести ресурсные связи от архива до подтверждённых blobs: изменился конкретный
   resource blob → повторить только связанные map / quest / UI checks. Не
   интерпретировать изменение всего PAK как необходимость заново исследовать
   каждую неизменную таблицу.
5. На следующем реальном патче измерить весь путь по фазам и размер ручной
   очереди. После закрытия обновлений — нагрузка нескольких аккаунтов, затем
   лёгкий Android runtime. Инструменты исследования остаются отдельно.

## Измеренный результат первого ускорения

На текущей публичной библиотеке новый импорт одного export с пятью functions
занял 16,991 секунды против 66 секунд полного импорта, повтор без изменений —
6,864 секунды. Таблицы кода совпали с существующим полным индексом.
Это замер индексатора, не всего обновления, Ghidra или авторизации.
[Методика, тесты и ограничения](evidence/tools/HEADLESS-INCREMENTAL-INDEX.md).

Критерии следующего приёмочного прогона: неизменные файлы не извлекаются снова;
неизменные inputs используют кэш; новые exports импортируются однократно;
повреждённый материал не меняет рабочую базу; каждый ручной пункт имеет причину,
evidence и следующую проверку. Фоновое расписание не создано: среда ранним утром
остаётся ориентиром, основание обработки — фактическое изменение файлов.
