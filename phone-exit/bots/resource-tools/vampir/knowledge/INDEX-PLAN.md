# План единого поискового индекса Vampir

Согласование архитектуры, 21 октября 2026. Это план, а не реализованный индекс.
Главный вход: [README](../../../vampir/README.md).

## Задача

Искать прежде всего в уже сохранённых данных. Повторно запускать Ghidra только
для отсутствующей функции, изменившегося источника или конкретной незакрытой
ветви. Один запрос должен находить код, строки, вызовы, документы и границы
проверки с обязательной привязкой к версии клиента.

Не пытаться сначала декомпилировать весь EXE. Исходные материалы уже сохраняются
в библиотеке ресурсов; индекс должен объединять их, а не заменять новыми копиями.
PAK / таблицы / карта и native-код имеют разные способы извлечения, но общий
учёт источников и общий поиск.

## Что мешает сейчас

`function-registry.py` связывает latest-export, entry-manifest, roles и questions
с одним SHA. Основной экспорт относится к старому EXE. Выгрузки новой сборки
находятся отдельно в details / bootstrap, поэтому исторический реестр помогает
с навигацией, но не служит полным актуальным поиском по новой сборке.

Предварительная инвентаризация двух каталогов новой сборки нашла 53 details и
22 bootstrap отчёта: 577 наблюдений / 173 разных адреса. Это подсчёт JSON inventory,
не подтверждённое покрытие EXE: receipts и SHA всех входов при подсчёте не сверялись.
Перед импортом нужна такая сверка; непроверенные данные не становятся фактами.

## Хранилища и ответственность

Существующие snapshots, Ghidra projects, экспорты и большие данные остаются
в `F:/PhoneExit Resources/Vampir/` по прежним путям. Массового переноса не делать.
Новый производный индекс размещать в `knowledge/search.sqlite3` библиотеки.
SQLite FTS5 проверен в установленном Python; отдельный поисковый сервер не нужен.
Базу можно удалить и целиком восстановить из проверенных входов.

В Git остаются importer / verifier / CLI, схемы, небольшие manifests, роли,
вопросы и документы. SQLite, EXE, PAK, Ghidra exports и реальные авторизационные
данные в Git не попадают. Runtime бота не зависит от Ghidra / поисковой базы.

## Идентичность и данные индекса

Основной ключ функции — **полный SHA EXE + адрес**, а не адрес или имя отдельно.
Один и тот же адрес в двух сборках не означает ту же функцию.

| Объект | Что сохранять |
| --- | --- |
| Версия | Полные SHA источников, manifest установки, версии как подписи, дата обнаружения |
| Артефакт | Путь, SHA, формат, tool/version, receipt, состояние проверки |
| Функция | SHA EXE, адрес, подтверждённые диапазоны, варианты имени |
| Наблюдение | Конкретный экспорт, псевдокод, инструкции, завершённость, warnings |
| Связь | Caller / callsite / callee либо vtable+slot; тип и доказательство |
| Строка | Текст, encoding, адрес / offset, источник, проверенные ссылки |
| Утверждение | Роль, метод проверки, ограничения, evidence и SHA применимости |
| Вопрос | Постоянный смысловой ID; отдельно ответы и unknowns по версиям |
| Ресурс | Путь / entry / ID / тип, SHA содержимого, связанные таблицы / виджеты |

Отдельно хранить адреса из документации с неустановленным типом. Само упоминание
адреса не создаёт функцию, caller edge или подтверждённую роль.
Совпадение функций между выпусками — отдельный кандидат связи; оно не переносит
роль автоматически. Общий вопрос может переживать несколько выпусков, но его
адреса и подтверждения должны иметь собственный SHA scope.

## Импорт и повторные выгрузки

Сначала инвентаризировать manifests / receipts, затем проверять source / output
hashes и поддерживаемую схему. Для каждого формата нужен явный adapter:
старый full export, comparison pairs, current details, bootstrap, native replay.
Не считать любой найденный JSON одинаковым доказательством.

Разделять состояния артефакта: обнаружен, проверен, повреждён, не поддержан.
Имя каталога, распознанная роль или успешное завершение процесса не заменяют SHA.
Replay импортируется как проверка указанного сценария с fixtures и limits,
а не как подтверждение всей функции / сессии.

Повторные наблюдения одной функции сохранять. Совпадающие байты / результаты
можно группировать; разные границы, псевдокод и имена показывать как варианты.
Позднейший экспорт не должен молча перезаписывать более полный прежний.
Противоречия попадают в явную очередь проверки. Ссылки всегда ведут к оригиналу.

Импорт неизменившегося артефакта пропускается по SHA. Пересчёт документации и
FTS не должен запускать Ghidra. Сборку индекса выполнять в отдельной базе:
проверить целостность, затем атомарно заменить активную базу. Не публиковать
частично собранный индекс.

## Поиск и запрос недостающего

Предлагаемый интерфейс одного CLI, ещё не реализован:

```text
knowledge-index.py build
knowledge-index.py verify
knowledge-index.py search "I_TID" --release installed
knowledge-index.py function <address> --release <SHA>
knowledge-index.py callers <address> --release <SHA>
knowledge-index.py question common-data-population
```

В выдаче: версия, что найдено, статус проверки, роль / гипотеза, ограничения,
ссылки на псевдокод / инструкции / доказательства. По умолчанию используется
проверенная установленная версия; её неизвестность явно сообщается, без
незаметного fallback к старому EXE. Историю можно искать отдельно или вместе,
но результаты разных SHA остаются визуально разделёнными.

После запроса функции CLI должен сообщать: материал уже есть; материал неполон;
функция ещё не выгружена; исходник изменился. Последние три состояния могут
создавать локальное задание Ghidra с конкретной причиной и ограниченным набором
адресов. После выполнения результат проверяется и индексируется. Автоматическое
расширение generic callers на весь EXE не включать.

## Обновления по средам

Пользователь сообщил: обычное обновление раз в неделю, по средам рано утром.
Точный час и timezone игрового расписания не установлены. Это ориентир для
проверки выпуска, а не доказательство его установки и не созданная автоматизация.

После завершения загрузки лаунчером:

1. Проверить стабильность файлов и создать manifest установки. Если чтение файла
   или установка меняются во время проверки, результат не считать новым baseline.
2. Сравнить источники с последним полным проверенным snapshot по SHA. Размер /
   mtime / выборочный fingerprint дают только предварительный фильтр.
3. Если поменялись PAK, переизвлечь изменённые доступные ресурсы и их зависимости.
   Неизменившийся EXE использует прежний кодовый индекс.
4. Если поменялся EXE, сохранить новый source snapshot, зарегистрировать отдельный
   release и выгрузить приоритетные функции входа / протокола / текущих unknowns.
5. Переносить связи как candidates. Перепроверить затронутые packet IDs, layouts,
   writers/readers, compiled tags и другие runtime зависимости.
6. Сформировать отчёт: совпало, изменилось, проверено, требует ручной работы.
   Старый индекс остаётся историей; runtime source guards не отключаются.

При загрузке обновления прежние материалы остаются доступны для поиска.
Сама среда не инвалидирует базу; фактическое изменение SHA создаёт новую версию.
PAK с зашифрованным индексом остаются ограничением извлечения: единый поиск
не должен показывать их как полностью разобранные.

## Порядок реализации и проверка результата

1. **Объединить существующее.** Inventory / validation adapters и SQLite индекс
   всех уже проверенных экспортов обеих сборок. Никакой новой декомпиляции.
2. **Подключить поиск.** FTS, функции / строки / edges / вопросы, стабильные ссылки.
   Добавить compatibility-вызов из function-registry, сохранив старые команды.
3. **Разделить версии знаний.** Перенести roles / claims и ответы вопросов в
   структуру с SHA scope без потери прежних evidence и ограничений.
4. **Подключить очередь Ghidra и обновления.** Существующие audit / snapshot /
   compare инструменты, зависимые проверки и очередь ручных unknowns.
5. **Добавить ресурсные adapters.** Таблицы / UI / карты в тот же поиск, с их
   собственными fingerprints и provenance, без подмены native registry.

Критерии первого этапа: повторный build не дублирует записи; повреждённый receipt
отклоняется; две версии одного адреса не сливаются; неполный экспорт не затирает
полный; каждый результат открывает существующий исходный материал; весь индекс
воспроизводится из manifests. Известные функции новой версии находятся без
запуска Ghidra. Экспорт отсутствующей функции становится новым материалом,
а поиск сам по себе не создаёт ни сетевой сессии, ни нового анализа.
