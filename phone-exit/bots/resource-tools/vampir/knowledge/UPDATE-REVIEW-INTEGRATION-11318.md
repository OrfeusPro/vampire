# Подключение подтверждённых проверок к обновлению 1.13.18

Регистрация исследовательского теста сама по себе не включает его в автопроход.
Для проверенного offline теста нужен `on_update=true` в `research-checks.json`;
известные функции для конкретного полного SHA также должны быть внесены в
`update-contracts.json`. Проверки, явно назначенные контракту, выполняются через
его `checks`; дополнительные `on_update` проверки попадают в `update_checks`
журнала. Результаты проходят существующий кэш по исходникам и зависимостям.
Нельзя заменять недостающий обязательный контракт набором дополнительных тестов.

Для SHA 1.13.18
`d30708283d893756b0fc1ffe700344be1a41fe746683106704b01ce32611532c`
подключены десять готовых launcher checks: shape, references, responses,
transport, common, JSON gates, caller fields, result getters, dispatch и response
callbacks. Внесены token/sign-in и их anchor bindings; основания и границы
сохранены в `release-update-targets.json` со ссылками на прежние evidence.
Непроверенные SDK/GMC2, runtime и игровые контракты не заменены.

Продолжение журнала `0e4e1d2aaa28535737a8648a5fdf28afc1e8fe0fa98e9d2bb009d9df214fb375`
27 октября 2026 прошло штатным `update --resume`: все десять checks — passed,
переиспользовано 9 этапов, новых Ghidra-запусков 0. Очередь уменьшилась со 150
до 148 строк после устранения двух незаполненных reviewed bindings launcher.
Состояние остаётся `needs_review`, profiles пуст, activation/baseline promotion
false. Дополнительные passed checks не означают готовый профиль или live login.
23 теста update contracts/bindings/run прошли.

После подтверждения нового участка следует сразу подключать повторяемую проверку
и правило поиска/валидации к этому процессу. На следующем SHA автоматически
переиспользуется механизм, а не недоказанный вывод о совместимости клиента.
