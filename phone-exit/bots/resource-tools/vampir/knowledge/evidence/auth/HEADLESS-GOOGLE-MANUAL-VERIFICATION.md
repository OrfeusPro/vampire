# Ручной Google-вход и почтовый код в очереди

Для клиента SHA256 `03edad26033c85835ad8fdc1825df7aeb635e2c199055598ad926bf84b43739f`
добавлен внешний браузер официального NID PCV2. Источник web:
[машинный контракт](../../google-verification-web-current.json), public `auth.js`
SHA256 `145539aa82203cc6d116938b505635275942ad5f65b0562983a0f8f35ddf85ac`.
Свежая HTML / JS копия получена с проверкой TLS, без cookies и входа в аккаунт;
прежние snapshots и указатели не заменялись.

В публичном коде подтверждены `showExternalBrowser` / `onIDPResponse`, Google
`googleIdKey`, внешний start / callback и GET-форма возврата SDK на `redirectUrl`.
Существующий экспорт OnResult `0x1450f3ef0` переиспользован: после преобразования
канала проверяется нулевой / ненулевой результат, принятые данные передаются
общим setters. Это статическая связь; новый native Google lifecycle не заявляется.
Готовые 3667 SDK сценариев и Launcher proof повторно не исполняются.

Мост слушает только `127.0.0.1` на выделенном ОС порту, с одноразовым путём из
256 случайных бит. Принимаются ограниченный GET, точные Host / path и ожидаемый
Google email в ID token. Эта локальная проверка связывает аккаунт, а проверку
подписи ID token выполняет официальный NID backend. Ответ возвращается в
`onIDPResponse` без ведущего `?`; SDK получает последующий Netmarble token
через существующий credential 33. Provider 29 не подменяется на email 20.
Обработчики URI Windows не меняются; внешняя вкладка остаётся у пользователя.

Для Google не читаются пароль Netmarble, пароль Gmail или IMAP. Официальные
окна устройства / защиты отправляют письмо; пользователь вводит код сам.
Непринятый ручной код остаётся в форме для исправления. Завершение требует
принятого серверного ответа и точного callback, после чего очередь продолжается.
Отмена / таймаут закрывают принадлежащие worker окна и loopback listener.
Этот путь поддерживает прямой выход ПК; Google через SOCKS и игровой мир
не подключены.

Проверки входят в `account-verification` и source check
`sdk-runtime-launcher-11316` текущего SHA: отдельный Google callback, сохранение
каналов, fixture Launcher composition, очередь без паролей / IMAP, управляемая
компиляция, возврат через настоящий loopback с проверкой nonce / email, UI.
Registry зависимостей и групповой кэш учитывают новые файлы и web evidence.
Fixtures и синтетический WebView smoke не подтверждают реальный Google-вход,
доставку письма, ввод пользовательского кода или игру онлайн.

Scoped исследование: `981bc2000d332d7ba1495a05f05b40524cccc9c3c67460789a36099ae6745bd7`.
Collect переиспользовал готовый экспорт без новой JVM.

В [живой проверке](HEADLESS-GOOGLE-MANUAL-VERIFICATION-LIVE.json) пользователь
вошёл через Google и ввёл коды самостоятельно. Worker вернул `verified` для
`device-registration` и `workplace`; очередь завершилась, процесс остановлен.
Первый вход новой записи теперь создаёт привязку из наблюдённых ключей ПК;
полная существующая привязка сохраняется. Результат не подтверждает Google
через SOCKS или игровой мир. Целостность web snapshot проверяется при каждом
Google-запуске; кэш source / tooling fixtures не выдаётся за свежую проверку сайта.
