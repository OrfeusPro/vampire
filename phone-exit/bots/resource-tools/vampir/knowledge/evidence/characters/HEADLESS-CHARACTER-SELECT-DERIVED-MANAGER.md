## Конструктор и идентичность

Существующий E8 scanner нашёл вызов базового конструктора `0x1455808c0`
по адресу `0x145cadbbb`, внутри функции `0x145cadba0`. Инструкции проверены
по границам PE unwind и затем экспортированы в Ghidra.

Factory `0x145cadba0`:

1. Запрашивает `0x2738` байт через `0x1468e4100`.
2. При null возвращает null без вызова базового конструктора.
3. Иначе исполняет базовый конструктор, записывающий глобальный singleton
   `0x14b573528`, затем ставит таблицу `0x1499e88c0` и обнуляет поле `+0x2730`.

В новом сценарии allocator возвращает ограниченный буфер. Вся функция factory
и базовый конструктор исполняются; проверяются итоговый указатель, глобальная
привязка, таблица и дополнительное поле. Настоящий getter `0x14558ee60`
затем возвращает этот объект обработчику ID110. Выбор factory клиентом при
настоящем запуске и заполнение экземпляра живыми данными ещё не проверены.

| Слот | Базовая таблица `0x1498ab150` | Производная `0x1499e88c0` |

## Настоящий путь переопределения

После принятия ID110 и записи `packet+0x20` в `manager+0x2728`:

- Вызывается `0x145cb9e90` через настоящую производную таблицу.
- Он исполняет базовый `0x1455910d0`. Его запросы через слот `+0x38` теперь
  выполняют настоящий `0x145ccad50`; lookup `0x145b03920` и accessor заданы
  отсутствующей записью. Backend `0x144aa3f40` также отсутствует в тесте.
- Настоящий getter `0x14558fa40(manager, 71)` читает u32 из записи 71.
  Глобальный байт `0x14b51f6b0` получает результат сравнения этого значения с 0.
- Настоящий getter `0x145564550` читает другой singleton. Значение его байта
  `+0x18` передаётся в производный слот `+0x60`, индекс 27; остальные аргументы
  равны `1, 0, 1, 1`. Этот слот здесь перехвачен, его эффекты не исполняются.
- После возврата обработчик продолжает прежний обход `0x14558d3f0`.

Getter `0x14558fa40` — 23 байта с проверкой `index < 205`, двумя RET и
чтением `manager+0x54+index*0x30`. Getter другого singleton — 8 байт.
Их точные байты закреплены в отчёте; идентичность второго объекта и смысл
байта `+0x18` не выводятся из одного адреса getter.

Статически прочитан `0x145cc64e0`: он вызывает базовый метод, обращается
к тому же реестру и в зависимости от полей записи может передать данные
другому менеджеру либо подготовить отправку через сеть. Конкретный пакет,
его wire-схема и эта ветвь пока не проверены. Называть этот вызов ID201 нельзя.

## Проверки и границы

18 полных сценариев: пять профилей записей × три значения внешнего байта
(0, 1, 255), плюс код 1 и два пути кода `0x1197`. Профили: пустой менеджер,
все активные получатели, выключенные флаги, нулевые counts и null-указатели.

При принятии проверены порядок вызовов, 205 запросов политики, перенос внешнего
байта без bool-нормализации и обновление глобального флага из записи 71.
Флаг не зависит от разрешения callbacks: у записи может быть значение при
выключенном флаге, нулевом count или null-получателе. Прежний refresh даёт
203 вызова только в профиле всех активных получателей. При отклонении ответа
переопределение не вызывается, глобальный sentinel `0xa5` сохраняется.

Allocator, реестр, accessor, backend конфигурации, внешние singleton-данные
и слот применения `+0x60` представлены ограниченными тестовыми границами.
Игра, аккаунт и сеть не использованы. Исходные восемь сценариев базового
менеджера повторно проверены; теперь тестовый конструктор выбирается отдельным
методом, чтобы исполнить производную factory без подстановки её таблицы вручную.
