## Класс и таблица фабрики

Строки регистрации и ссылки на конструкторы подтверждены инструкциями:

| Класс | Регистрация | Конструктор | Основная таблица |
| --- | --- | --- | --- |
| `/Script/Engine.GameInstance` | `0x143bf3b90` | stub `0x143bf62e0` → `0x143bf9f20` | `0x14929a098` |
| `/Script/ProjectRED.RdGameInstance` | `0x1468e10e0` | `0x1468e30f0` → базовый `0x1454d2b00` | `0x149e0d4d8` |

Базовый конструктор `0x1454d2b00` вызывает конструктор GameInstance и
ставит промежуточную таблицу `0x149866e58`. У всех трёх основных таблиц
слот `+0x3d0` равен `0x143c05a10`, слот `+0x3e0` — `0x14178c590`.
Метод `+0x3e0` копирует указатель класса из входного аргумента в выходной;
при включённом GC дополнительно вызывает `0x1416dceb0`.

В новом сценарии настоящий `0x1468e30f0` устанавливает таблицу RdGameInstance.
Его базовый конструктор перехвачен. Адрес фабрики читается из установленной
таблицы, затем исполняется вся функция и настоящий метод `+0x3e0`.
Запись такого GameInstance в поле настоящего мира `+0x1d8` этим не проверена.

## Источники класса внутри фабрики

Параметры фабрики: RCX — provider, RDX — объект URL, R8 — мир.
При нулевом R8 мир берётся через `[provider+0x30]+0x2c0`.
Затем `0x144319a30(world, false, true)` возвращает объект, из которого
читается класс по смещению `+0x348`. Дескриптор `0x14915bda0` содержит
имя `DefaultGameMode` и то же смещение `0x348`.

Статический разбор показывает дополнительные ветви:

- Перебор URL options `[url+0x48]`, количество `[url+0x50]`, поиск `GAME=`
  через `0x1415893d0`. Непустая строка обрабатывается `0x141beb250`, затем
  загружается класс через `0x1417e2ea0`. Валидный результат заменяет исходный.
- При отсутствующем / неподходящем классе используются имя карты из URL,
  обработка префикса `UEDPIE`, helper `0x141beafb0` и повторная загрузка.
- При дальнейшем отсутствии класса вызывается `0x141beb510` и ещё одна
  загрузка. Семантика всех его настроек здесь не восстановлена.

Эти ветви не исполнялись. Поэтому имя уровня или импорт Blueprint сами по
себе не доказывают активный GameMode. Параметры загрузки и запасные настройки
могут влиять на выбор; их реальные значения после ID110 ещё неизвестны.

## Восемь исполненных сценариев

Проверены все сочетания трёх условий:

- мир передан явно либо получен через provider context;
- один из двух разных валидных классов задан в поле `+0x348`;
- создание возвращает объект либо null.

В обоих вариантах мира функция передаёт одинаковый world pointer в границу
создания. Разные классы из `+0x348` доходят через настоящий метод `+0x3e0`
до `0x143daecc0(world, class, 0, 0, parameters)`. Результат этой границы
сохраняется через очистку URL и возвращается в RAX, включая null.

Проверяется полный возврат функции с лимитом инструкций; неожиданный адрес
исполнения останавливает сценарий.

## Границы и продолжение

Перехвачены базовый конструктор, получение WorldSettings, операции с пустыми
строками, подготовка параметров создания, само создание, очистка URL и проверка
stack cookie. Метаданные наследования классов и provider context заданы тестом.
GC выключен, URL options / имя карты / portal пусты. Не проверены ошибочные
классы, ветви `GAME=` / fallback, настоящий loader и вызов `0x143daecc0`.

Следующий шаг — получить реальные параметры загрузки после ID110 и проверить
связь данных уровня с `DefaultGameMode`; при необходимости разобрать ветвь
`GAME=`. Полную модель движка переносить в бота не требуется. Сетевой клиент,
устройство, реальный вход и мировая позиция остаются открытыми.
