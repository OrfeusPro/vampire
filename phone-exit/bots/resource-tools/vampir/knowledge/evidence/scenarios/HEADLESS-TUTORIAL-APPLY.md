## Что теперь проверено исполнением

`replay-release-tutorial-apply.py` исполняет целые функции:

- `0x141682d60` — поиск ожидающего ключа;
- `0x14163c5f0` — исключение ячейки из hash chain;
- `0x14163c480` — изменение free list и allocation bit;
- `0x1464c06d0` — выбор отложенного / немедленного применения;
- `0x1464c4ea0` — копирование и постановка ID 9904 в подготовленную очередь;
- `0x1464d1770` — перенос записи в серверное и локальное состояния;
- constructor / getter ID 9904 и constructor вложенной записи.

Таким образом, `0x141682d60(context+0x268, key)` действительно удаляет ожидающий
ключ, а не только проверяет наличие. 12 сценариев покрывают первый / средний /
последний элемент цепочки, key 0 / 1001 / 0xffffffff, inline / external buckets
и allocation flags. Проверены цепочка оставшихся ключей, очищенный allocation
bit, free list, повторное удаление и отсутствующий ключ без изменения хранения.
Lookup / unlink / sparse free не заменены fixtures.

## Серверная запись и локальный шаг

384 сценария применения покрывают существующую / отсутствующую серверную запись,
наличие / отсутствие локальной задачи, inline / external hash buckets,
selector 0 / 2 / 0xffffffff, state 0 / 1 / 2 / 3, оба значения keep и gate.
Проверены коллизии, uint32 переполнение и сохранность посторонних записей.

| Область | Изменение |
| --- | --- |
| Серверный map context+0xa8 | Сохраняются raw08, raw0c, raw10 и state входящей записи |
| Локальный map context+0x1c8 | При наличии ключа копируются raw08, raw0c и state; прежний raw10 сохраняется |
| Gate возвращает ненулевой AL | После копирования локальная запись дальше не продвигается |
| Gate возвращает 0, keep равен 0 | Локальный raw0c увеличивается на 1 с uint32 переполнением |
| Gate возвращает 0, keep ненулевой | Локальный raw0c сохраняется |
| Gate возвращает 0, входящий state равен 0 | Локальный state становится 1 |

После разрешённого перехода вызывается запуск задачи с локальной записью и
её выбранным селектором. Без локальной задачи серверная запись обновляется,
но gate / запуск не вызываются. Серверный raw0c не подменяется локальным +1.

Свежая вставка серверной записи, реальный gate `0x1464c5770` и запуск задачи
`0x1464cfb80` — явные fixtures. Для существующих записей native lookup и stores
исполняются без подмены. Проверка ещё не доказывает фактическое выполнение задачи.

ненулевой третий аргумент, keep и результат gate.

При нулевом третьем аргументе и состоянии клиента `<6` native код копирует

Проверены code, все поля вложенной записи и оба флага. Изменение исходного пакета
после постановки не меняет копию. Ожидающий ключ и оба map остаются прежними.

При состоянии `>=6` или ненулевом третьем аргументе receiver удаляет ожидающий

Это проверка явного обхода раннего условия; автоматический потребитель очереди
и его lifecycle пока не исполнены. Связывать ID 206 с native состоянием 6
по одному совпадению порядка событий нельзя.

Clone allocation и получение состояния клиента — fixtures. Очередь имеет
подготовленную ёмкость; её рост и освобождение копий ещё не проверены.

## Уточнение функции допуска следующего шага

Повторно прочитаны инструкции `0x1464c5770`, без нового экспорта. В отличие от
угаданного Ghidra `void`, инструкции явно возвращают AL:
нет descriptor → 0; selector отличается от descriptor+8 и state не равен 2 → 0.
После ветвей завершения / cleanup выставляется AL=1. Это статический вывод;
полный native replay функции с её побочными эффектами ещё не выполнен.
Нельзя присваивать descriptor+8 имя колонки CSV без проверки loader.

Следом — lifecycle потребителя очереди, loader TutorialStep и реальные условия
первой задачи / callback панели. Нужны две отдельные модели: полученное серверное
состояние и выполняемый локальный шаг. Текущие raw0c 0 / state 1 сами по себе
по-прежнему не доказывают ожидание step 2.

Для продолжения найдены и проверены границы прямых CALL к `0x1464d1770`:
`0x1464cd590` вызывает его по `0x1464cd607` / `0x1464cd682`,
`0x1464d0510` — по `0x1464d0aae`. Это кандидаты следующих ветвей применения;
их связь с потребителем очереди ещё не установлена. Не начинать новый поиск
того же helper вместо разбора этих конкретных callers.
