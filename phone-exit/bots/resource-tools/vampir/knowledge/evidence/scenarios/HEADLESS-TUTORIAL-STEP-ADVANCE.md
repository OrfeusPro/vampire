Использованы сохранённые [живые записи](HEADLESS-LIVE-TUTORIAL-STATE.md),

## Что установлено

`0x145c25f20` ищет строку по первому ключу. `0x145c2e8b0` сначала выбирает
группу по этому ключу, затем перебирает указатели строк и сравнивает их поле
+0x18 с переданным вторым параметром. Receiver передаёт в этот поиск ключ
записи и raw0c. Это статически подтверждает роль raw0c как селектора строки
внутри группы; имя поля структуры ещё не переносится в runtime автоматически.

Целая функция `0x1464cd6f0` исполнялась в 64 native-сценариях:

- Если fixture `0x1464c5770` возвращает ненулевой AL, поля не меняются,
  `0x1464cfb80` не вызывается.
- Иначе при нулевом третьем аргументе raw0c увеличивается на 1 с uint32
  переполнением; при ненулевом аргументе остаётся прежним.
- Только state 0 меняется на 1. Остальные проверенные state 1 / 2 / 3 сохраняются.
- В `0x1464cfb80` передаются контекст, запись и выбранное значение raw0c.
- Нулевая запись ничего не вызывает.

Таким образом, сохранённые raw0c=0 / state=1 сами по себе не доказывают
ожидание step 2. При прохождении изученной ветви с нулевым третьим аргументом
выбранное значение станет 1; реальные условия допуска ещё нужно подтвердить.

В актуальном CSV TutorialStep (SHA256
`b40d28346c5bb53e93f3e00ed634ac2c9322cd2ecc3cc589983073c72e83c8e7`)
для Tutorial 1001 есть две строки:

| Id | Step | TaskType | TaskParam | ServerProcessRequest |
| --- | --- | --- | --- | --- |
| 1001001 | 1 | 4 | 1 | 0 |
| 1001002 | 2 | 16 | QuestPanel_PanelTouch | 1 |

Связь имени Step с native row+0x18 пока не подтверждена loader / schema proof.
Совпадение структуры поиска — ориентир для следующей проверки, не готовая
модель текущего шага.

## Запуск задачи и границы

Статический `0x1464cfb80` получает строку через `0x145c2e8b0`, сохраняет
селектор в raw0c и разветвляется по byte row+0x30. Ветвь 4 вызывает constructor
`0x1464dc4c0`, ветвь 16 — `0x1464dc3d0`; затем вызывается virtual slot +0x10
с указателем строки. Это кандидаты пути первой задачи и нажатия панели.
Имена TaskType ещё требуют проверки соответствия row layout.

Реальный `0x1464c5770` включает lookup, проверки состояния, вызовы завершения /
cleanup и callbacks; он не является простым чистым предикатом. Ghidra показывает
shared branches, void return и подозрительную запись `DAT_00000014`.
Не переносить эти конструкции из псевдокода напрямую. Native-проверка перехода
явно заменяет весь этот вызов заданным AL и не доказывает его реальные условия.
Внутренности запуска `0x1464cfb80` также не исполнялись.

Следом — loader / layout строк группы, инструкции вокруг AL вызываемой функции,
инициализация задач `0x1464dc4c0` / `0x1464dc3d0` и их callbacks. До этого
не отправлять `PktQuestPanelSelect` как замену выполнению обучения.
