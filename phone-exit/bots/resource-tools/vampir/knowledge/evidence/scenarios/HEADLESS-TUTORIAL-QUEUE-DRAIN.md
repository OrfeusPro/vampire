## Найден настоящий вход функции

Caller `0x1464cd590` оказался внутренним chained-unwind фрагментом функции,
начинающейся с `0x1464cd550`. Перед ним находятся пролог, сохранение контекста,
проверка готовности и начало обхода. Полная функция состоит из шести связанных
unwind ranges до `0x1464cd6ef`. В native replay исполняется настоящий вход
и все принадлежащие ему ranges, а не вызов внутреннего фрагмента как функции.
Автоматический collect правильно отказал для неоднозначного внутреннего адреса;
новый экспорт запрошен только для подтверждённого начала.

При byte состояния клиента `<6` функция возвращается, сохраняя очередь.
Иначе она обходит context+0x198 в исходном порядке, пропускает нулевые указатели,
разветвляется по ID пакета и передаёт каждый ненулевой пакет в virtual destructor
с флагом 1. После обхода native код обнуляет число элементов; при ненулевой
ёмкости вызывает helper её сокращения. Функция содержит ветви ID 9902 / 9904 /
9905 / 9907. Проверка исполнения ниже относится к ID 9904.

Для ID 9904 выполняются настоящее удаление ключа из context+0x268 и
`0x1464d1770(context, packet+0x18, packet.raw31)`. Порядок сохраняется и при
нескольких ответах с одинаковым ключом: первый удаляет его, повторное удаление
не освобождает ячейку второй раз. Серверная и локальная записи остаются раздельными.

## Проверка исполнения

`replay-release-tutorial-apply.py --drain` добавляет 64 сценария к прежним
12 / 384 / 32 проверкам удаления, применения и раннего ответа:

- Исходные состояния клиента 0 / 5 / 6 / 7.
- Пустая очередь, одна нулевая ячейка, один ответ, два ответа с нулевой ячейкой между ними.
- Оба значения keep и заданного результата gate.
- После раннего возврата состояние меняется на 6 и вызывается тот же consumer.
- Проверяются сохранность отложенных записей до готовности, порядок применения,
  передача пакетов на освобождение по одному разу и native сброс count до shrink.
- Повторный вызов после опустошения не применяет и не освобождает пакеты заново.

Native исполняются consumer со всеми его unwind-фрагментами, lookup / unlink /
sparse free ожидающего ключа, применение записи и lookup существующих maps.
Получение клиентского состояния, gate задачи и запуск — прежние явные fixtures.
Virtual destructor пакета и shrink / free очереди также заменены ограниченными
fixtures. Последний проверяет native count=0 до вызова и моделирует освобождение
подготовленной очереди. Реальные deallocation и рост очереди не исполнялись.

```powershell
python -X utf8 -m unittest discover -s phone-exit/bots -p test_vampir_tutorial_drain.py
```

Проверка `release-tutorial-drain` работает offline. Прежняя проверка
`release-tutorial-apply` остаётся отдельным запуском без нового consumer.
Ни авторизация, ни игровые команды не выполнялись.

## Драйвер и начальное уведомление: пока статически

Проверенный прямой CALL `0x1464cd2de` ведёт в consumer. Сам caller тоже состоит
из chained-unwind ranges: начало `0x1464cd1e0`, а `0x1464cd2c5` — внутренний фрагмент.
В Ghidra видны условия: нулевой глобальный byte `0x14b2f314b`, существующий owner,
проверка его типа и результат owner virtual +0xa18, равный 3. Перед вызовом
consumer драйвер очищает набор ожидающих ключей context+0x268 и выставляет
глобальный byte `0x14b5f3dc9`. Это ещё не доказательство вызова на каждом кадре
или после конкретного сетевого ID; driver целиком не исполнялся.

Ветвь queued ID 9905 передаёт packet+0x10 в `0x1464c4ba0`. Статический helper
для каждой записи проверяет наличие строки Tutorial, вызывает вставку / обновление
серверного map через `0x1464a1460` и проверяет сочетание local state 1 / server
state 2. Для непустого входного массива в конце вызываются `0x1464c67e0` и
`0x1464cfeb0`. Пустой массив возвращается без этих вызовов. В этом helper флаг
уведомления не используется как универсальная команда завершения.

`0x1464cfeb0` получает набор статусов через `0x1464d0510` и для подходящих
элементов вызывает `0x1464cd6f0(..., local_record, 0)`.
`0x1464d0510` перебирает серверные записи, учитывает row lookup и локальные задачи;
это другая ветвь построения статусов, а не потребитель очереди.
Полное исполнение notify helper / построения статусов и их зависимости от таблиц
пока не проверены. Наличие ключа 1001 в живом уведомлении не доказывает запуск
конкретной задачи без этих условий.

Следом — native применение начального ID 9905, построение локальных задач,
loader TutorialStep и реальные условия первого перехода. Native состояние 6 /
условия драйвера ещё нужно связать с lifecycle бота; ID 206 сам по себе такой
связи не устанавливает. Кнопка продолжения и ID 9903 пока не подключены к отправке.
