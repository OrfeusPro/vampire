# Шаги Time квеста 110110 на клиенте 1.13.22

Проверка относится к EXE с SHA256
`03edad26033c85835ad8fdc1825df7aeb635e2c199055598ad926bf84b43739f`.
В текущем `QuestTask.csv` у квеста четыре строки Time. Для проверок используются
индексы строк в порядке таблицы квеста. Все десять строк имеют пустую группу сервиса.

| Задача | Индекс строки квеста | Длительность, секунды |
|---|---:|---:|
| 110110010 | 0 | 0,1 |
| 110110020 | 1 | 0,1 |
| 110110035 | 3 | 0,1 |
| 110110100 | 9 | 0,1 |

Исполнитель связывает текущие callback, start, tick, timer, completion и
постановку команды в очередь. Для таймера граница текущей функции начинается
по `14549a7d0`. Сравнение всех инструкций проверяет вызовы, переходы и данные.
Загруженные в стенд модели, игровой цикл, доступность персонажа и разбор JSON
представлены явно заданными providers. Готовые результаты проверки списка
квестов и формата пакетов используются повторно.
[Контекст и исходные выгрузки](../../native-contexts/quest-time-current.json).

Целая функция `1455ca1f0` строит свойства `QuestInfoId` и `QuestTaskIndex`.
Функция `1455ca000` ставит запись с selector `1`, проверяя уже ожидающую
команду с тем же ключом. Это локальная граница исполнения Time.
Пройдены 68 сценариев, 476 проверок Win64 ABI и 3 432 проверки возврата
из фикстур. В открытом сценарии два приращения по 0,05 секунды переводят таймер
в состояние ожидания завершения. Следующий тик вызывает completion. Пока запись
ожидает отправки, повторный completion оставляет одну запись для этого квеста.
Проверены также другой ключ, другой selector, другой индекс при том же ключе,
запрет ожидающей команды и смена состояния модели.
[Машинный результат](QUEST-TIME-CURRENT-VALIDATION.json).

Для отправки `1810` функция `145d72d80` берёт три компонента из
`actor.component + 0x1f0` либо значение из `14b0c3298` при отсутствии
компонента. Отсутствующий в свойствах Time `TargetId` преобразуется в `0`
через пустую строку и `_wtoi64`. В файле по резервному адресу лежат нули, а страница данных
доступна для записи. Состояние этих полей в живом процессе требует отдельного
источника. Текущая сессия выдаёт серверную точку входа до коррекции позиции.
В её пакете доступен подтверждённый ручной старт, а выполнение шагов ждёт
нового допуска. Квест принят сервером и остаётся на индексе `0`.
[Доказательство живого старта](QUEST-START-CURRENT-ONLINE.json).

В исторической записи официального клиента первый запрос `1810` содержал
`110110`, индекс `0` и `TargetId=0`. В мире `10010` компоненты X и Y
совпали с ответом входа `206`, а Z отличалась на +54,807. Первые 12 байт
предшествующего исходящего `305` совпали с вектором `1810`. Сервер ответил
`1811` с кодом `0`, состоянием `2` и индексом `1`. Эти значения относятся
к записанному входу и дают ориентир для проверки перехода. Точная версия
официального клиента записи неизвестна. Текущие координаты Bipoberiho и
ответ сервера на новый запрос предстоит получить отдельно.
[Границы исторической записи](../scenarios/HEADLESS-QUEST-REFERENCE-TIMELINE.md).

Штатное обновление вызывает `quest-time-current` через контракт `quests`.
Ключ результата включает точный EXE, принятые экспорты, именованную таблицу,
архив и входы инструментов. Неизменный проход проверяет готовую квитанцию.
Следующее решение зависит от проверенного источника координат персонажа и
правила сопоставления `1811` с переходом активной задачи.
