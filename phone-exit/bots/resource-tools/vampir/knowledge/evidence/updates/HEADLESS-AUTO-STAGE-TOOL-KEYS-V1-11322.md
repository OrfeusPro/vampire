# Ключи инструментов разрешения адресов и проекций

[Машинное правило](../../binding-tool-scope.json) задаёт два корня группы
bindings — update-bindings и binary-diff-candidates. Они разрешают рецепты
по точному EXE и используют текущие native / PE helpers. Общий каталог
function-reuse и модель contracts имеют собственные входы и проверки.
Их посторонние инструменты исключены из ключа разрешения адресов.

BinDiff reader становится границей обхода только при точном зарегистрированном
SHA файла. Проверенные checked_comparison / checked_export / candidates читают
JSON, SHA и SQLite и используют функции того же модуля. При изменении кода
прежняя граница снимается и скрипт обходит его зависимости консервативно.
Новые зависимости resolver также находятся обычным обходом. SHA правила
входит в ключ и общие определения прохода. Выбранный knowledge передаётся
в каждый начальный и финальный сбор execution inputs.

На текущем дереве инструментов группа сократилась со 197 до шести файлов,
включая правило. Остальные пять групп совпали с прежним алгоритмом на тех же
файлах. Конкретная проверка одного unwind root в сохранённом EXE выполнилась
один раз. Два повтора использовали Journal cache, включая key-model изменение
постороннего native tool. Реальные файлы при этом сохранялись. Проверка root
подтверждает только статическую границу, роль и semantic готовность не повышены.

Проекции Version / Login используют SHA своего контекста и projection.inputs
вместо дополнительной общей группы context tools. Их ключ уже включает rule,
сохранённые fixture tools, публикации и транзитивные использованные файлы /
runtime. Prepare, observe и свежий finish сохраняются. Native materialization
и старые context adapters продолжают использовать свои прежние ключи.

Общий набор завершил 1516 тестов с тремя прежними пропусками. Отдельный
controller check завершил 37 тестов, projection routing — четыре. Добавлены
четыре сценария контроллера и один проекций. Проверены повтор после постороннего
изменения, пересчёт после изменения PE-reader / правила / нового helper,
возврат полного обхода изменённого BinDiff и использование выбранного knowledge.
Шесть дополнительных checks прошли.

Первый запуск с новым форматом binding key создаёт собственный результат.
Последующие неизменные запуски его переиспользуют. Полный updater и native
сценарии этой приёмкой не запускались.

Далее остаются консервативные остальные группы, план affected / readiness
и ключ native-materialize. Их сужение требует отдельной проверки фактически
исполняемых зависимостей. Полный проход после изменений также остаётся
отдельной приёмкой.
