# Vampir: проверка окна с побочными эффектами

15 октября 2026. Продолжение [ENTRY-WINDOWS.md](ENTRY-WINDOWS.md).
Важное уточнение: `0x144a1cbf0` нельзя описывать как чистый IsVisible/Contains.
Его успешная ветвь вызывает другие операции до возврата true.

Источник — Windows Shipping EXE, SHA256
`c7552efd2125e7981945d3443cc1d70a41ac0a8a4cb42e7c77e0d40b4713dfc8`.
Это инструкции собранного клиента, не имена из исходного C++.

## Воспроизведение

`python phone-exit/bots/resource-tools/vampir/build-ui-manager-code.py`
после build-entry-window-code.py. Нужен закреплённый Capstone 5.0.6.
Отчёт: `F:/PhoneExit Resources/Vampir/code-clues/ui-manager-code.json`.
Десять корней, 24 фрагмента и отдельный leaf callback; 1523 инструкции,
десять групп наблюдений с проверкой
точных адресов/операндов. Для каждого фрагмента сохранены байты и SHA.
Генератор отклоняет изменившийся EXE или неизвестную якорную инструкцию.

## Что делает `0x144a1cbf0`

1. Сохраняет входной RDX как искомый объект. Берёт начало списка из `[RCX+0x18]`,
   число записей из `[RCX+0x20]`; шаг записи — восемь байтов.
2. Вызывает `0x1417f24d0` для каждой записи и сравнивает результат с объектом.
   Если объект не найден, возвращает AL=0 без перехода к успешной ветви.
3. Если найден, повторно получает последнюю запись списка. Пока она отличается
   от искомой, вызывает `0x144a240d0` с EDX=1 и снова проверяет хвост/число записей.
4. При совпадении последнего объекта вызывает его виртуальный слот +0x520,
   затем `0x144a27a50` с этим объектом и R8D=0. Только потом возвращает AL=1.

Это поиск и обработка найденного окна в списке, а не пассивная проверка видимости.
По структуре похоже на возврат к существующему окну в стеке, но имя/тип структуры
и все контракты пока не доказаны. Не называть +0x520 «OnShow» только по позиции.

## Что известно о соседних операциях

`0x144a240d0` смотрит предпоследний элемент, вызывает виртуальные слоты +0x4f0,
+0x4f8 и другие функции; присутствует передача делегата и вызов `0x144a2a530`.
Удаление теперь найдено в `0x144a2a530`: последний элемент берётся по
`[array + count*8 - 8]` в `0x144a2a589`, а число элементов уменьшается
инструкцией `dec dword ptr [rdi+0x20]` в `0x144a2a791`.
После этого вызывается обработка массива по адресу `[rdi+0x18]`.
Момент исполнения callback и точная длительность перехода пока не установлены.

`0x144a24f80`, вызываемый последующим блоком презентации, также читает список
+0x18 / число +0x20 и сравнивает последний объект с входным. Перед этим проверяет
входной RDX на null; дополнительные флаги меняют дальнейшую обработку.
Поскольку часть флагов пока не названа, сигнатуру ShowWindow из них не строить.

`0x144a55e30`, встречавшийся в пути ServerSelectPopup, вызывает виртуальный
метод со значением DL=4, меняет поле состояния +0xe10 и выполняет другие
операции. Число 4 не подписывать как Visible: enum именно этого метода неизвестен.
Его инструкции сохранены в том же отчёте для следующего разбора.

## Завершение, сброс и немедленный путь

`0x144a5aef0` проходит массив +0xa08 с шагом64байта. Для ненулевого адреса
callback получает payload и вызывает его через `call rsi` (0x144a5af40).
После обхода очищает записи, обнуляет count+0xa10, затем записывает state+0xb40:
из0 получается1, из остальных значений3. Это порядок инструкций **до** последующих
ветвей: при флаге+0xb5c может переноситься вторая очередь+0xa18 и запускаться
следующий переход. Поэтому state3 не обязательно остаётся конечным состоянием.

Важен порядок: callbacks исполняются **до** установки state1/3. Нельзя выводить
из этих данных, что при исполнении callback состояние уже3, или предполагать
одинаковое поведение повторного добавления во время обхода. Reentrancy и изменение
очереди самим callback ещё не проверены.

`0x144a4ca20` — отдельный путь очистки: обработка двух массивов+0xa08/+0xa18,
обнуление их count, установка state1. В нём нет цикла dispatch из функции
завершения. Предшествующий вызов0x144a7b5e0 и функции очистки ещё не разобраны;
это не полное доказательство семантики отмены и не гарантия сохранения callbacks.

`0x144a5a650` сравнивает замаскированное поле+0xb60 с float32-константой
`9.99999993922529e-09` (байты77cc2b32, offset144305088 EXE).
При обычном конечном значении не больше порога исполняются вызовы update-helper
0x144a5b0f0 и завершения0x144a5aef0 напрямую. JA ведёт к другой ветви,
где вызывается0x1445d0f70 для подобъекта+0xa30. Его запуск и обратная связь
к завершению пока не восстановлены. Единицы+0xb60 не доказаны: не называть
константу временем в секундах. NaN и runtime-default отдельно не проверены.

Значит, фиксированная пауза не может заменить проверку результата перехода:
быстрый и обычный пути различаются, вторая очередь может запускать новый переход,
а reset не эквивалентен dispatch. Пока бот ждёт по распознанному экрану;
новые правила ожидания/кликов на основании только этих чисел не добавлялись.

## Значение для входа и бота

### Путь удаления через callback

В переходной ветви `0x144a240d0` инструкция `0x144a24236` загружает адрес
`0x144a1ce60`. В payload записаны объект менеджера (RDI) и аргумент (ESI);
адрес callback и payload передаются в `0x144a720c0`.
Этот helper переносит float-параметры в другой объект и передаёт callback
в `0x144a48d20`. Смысл float-параметров и запуск callback ещё не восстановлены:
называть их точным временем анимации пока нельзя.

Leaf callback `0x144a1ce60–0x144a1ce85` не имеет записи unwind; он разобран
от проверенного входного адреса до RET, padding/соседние функции исключены.
Он проверяет доступность глобального объекта, читает аргумент `[RCX+8]`,
читает владельца `[RCX]`, затем хвостовым JMP вызывает `0x144a2a530`.
Если проверка глобального объекта не проходит, callback возвращается.

Таким образом, прямая ветвь `0x144a2429f` и callback ведут к одному месту
уменьшения списка. Это доказанная связь управления, но не доказательство,
что callback выполнится при любых условиях. Время/отмена/повторный вызов
по-прежнему требуют изучения принимающего объекта.

Ветка CharacterSelectUI вызывает `0x144a1cbf0` и при true пропускает следующий
блок презентации. Теперь известно, что эта ветка сама может обрабатывать другие
окна; утверждение «true означает только уже видно» было бы неверным.
При восстановлении сценария нужно учитывать изменения окна после этой операции.

Бот не вызывает эти нативные функции. Его действия по-прежнему требуют
распознанного экрана/цели и проверки результата; источник объясняет логику клиента.
На Android ничего не исполнялось. Следующий шаг — контракт выполнения/отмены
callback, виртуальных методов, флагов и связь с кадрами.

### Очередь callback

В0x144a48d20 проверяется поле+0xb40. Значение2 выбирает ветвь, где
увеличивается count+0xa10 и формируется запись размером64байта в массиве+0xa08.
Значение3 выбирает ветвь непрямого хвостового вызова callback. Имена состояний
и триггер завершения очереди ещё неизвестны; номера не сопоставлены с enum
видимости. Эти инструкции и ветви включены в проверяемый отчёт.
