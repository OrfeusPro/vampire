# Vampir: обычный переход через easing и callback

15 октября 2026. Продолжение [UI-MANAGER.md](UI-MANAGER.md).
Источник: Windows Shipping EXE SHA256
`c7552efd2125e7981945d3443cc1d70a41ac0a8a4cb42e7c77e0d40b4713dfc8`.
Это исследование собранного клиента, а не проверка runtime Android.

## Воспроизведение

`python phone-exit/bots/resource-tools/vampir/build-ui-transition-code.py`
после build-ui-manager-code.py. Используется закреплённый Capstone5.0.6.
Отчёт: `F:/PhoneExit Resources/Vampir/code-clues/ui-transition-code.json`.
Десять корней, двадцать фрагментов + leaf-wrapper, 919 инструкций, семь групп
проверенных связей, 15 ссылок на текстовые литералы. Хеши EXE/отчёта, диапазоны,
байты инструкций и смещения сохранены. Изменившиеся якоря прекращают генерацию.

## Связь обычного запуска с завершением

1. В настройке `0x144a4c440` сохраняется владелец и адрес callback
   `0x144a45830` в блоке начиная с поля +0xac0.
2. Обычный путь, найденный ранее, передаёт подобъект +0xa30 в leaf-wrapper
   `0x1445d0f70`. Он передаёт конфигурацию из +0x20 в `0x1445d0bd0`.
3. Здесь копируются настройки и два блока callback. Конкретно второй блок
   копируется из config+0x70 в controller+0x90. Смещения согласуются:
   +0xa30 +0x20 +0x70 = +0xac0 основного объекта.
4. Диагностика идентифицирует функцию как `FNnEasingVar::Start()`.
   При неверном результате выбора функции есть `invalid Function`, а при
   отказе `0x1445d33b0` — `failed to _StartTimer()`.
5. `0x144a45830` проверяет разрешение сохранённого владельца. Если проверка
   успешна, вызывает обновление `0x144a5b0f0`, затем завершение очереди
   `0x144a5aef0`. При неуспешной проверке тело пропускается.

Теперь подтверждён и условный путь **tick таймера → второй callback**,
см. следующий раздел. Цепь не безусловна: запуск таймера может отказать,
владелец может стать недоступен, возможны повторение и отдельная остановка.

## Обработчик таймера и завершение

`_StartTimer` в `0x1445d34d1` получает адрес `0x1445ccb90`, сохраняет его
в объект callback (+0x20) вместе с владельцем (+0x18). Это зацепка регистрации
обработчика. Контракт самого native timer manager до конца не восстановлен.

Обработчик `0x1445ccb90`:

- Пропускает работу при нулевом handle+0x10 либо пока current ticks меньше
  границы+0xe0. Тип/единицы ticks отдельно не переименовывались.
- Вычисляет прошедшее значение, ограничивает его полем+0xf0, сохраняет в+0xe8
  и вызывает update `0x1445d31d0`.
- Если+0xe8 достигло+0xf0, хвостовым JMP вызывает `0x1445d2f70`.

Update вызывает выбранную easing-функцию через указатель+0xf8, сохраняет
текущее значение+0xd8 и при наличии первого callback(+0x50) передаёт ему значение.

Завершение `0x1445d2f70` может сначала довести значение до выбранной границы
и вызвать первый callback. Затем увеличивает счётчик+0x104 и сравнивает с+0x40.
Если предусмотрен ещё проход, переходит в ветвь повторного `_StartTimer`,
при отдельном флаге переключает+0x108. Точные имена флагов не установлены.

В конечной ветви снимается таймер через вызовы менеджера, затем **до** второго
callback обнуляются handle+0x10 и поле+0xe0. Указатель второго callback берётся
из+0x90 и, если он ненулевой, вызывается в `0x1445d30db` с текущим значением.
Именно этот слот получил callback завершения UI из предыдущей привязки.
Связь к телу `0x144a45830` и далее к выполнению очереди таким образом сошлась
по слотам и вызовам; фактический запуск на Android ещё не проверялся.

## Отдельная остановка и перезапуск

Helper `0x1445d2690` проверяет флаг+0x44 и handle+0x10, обращается к таймерному
менеджеру и обнуляет handle при успешном пути. В этом helper нет dispatch
второго callback. Не подменять его завершением: удаление таймера само по себе
не означает выполнение очереди UI.

`_StartTimer` вызывает этот helper перед подготовкой нового таймера в своей
ветви для+0x44=0. Это подтверждает путь остановки прежнего таймера при повторной
подготовке, но полная цепочка reset окна→stop helper пока не установлена.
Поведение при недоступном менеджере и изменении очереди из callbacks требует
отдельной проверки; гарантии exactly-once пока не заявляются.

## Что известно о визуальном элементе

Настройка ищет имя `ImageFader`, затем `Color`. Обновление строит имя `Percent`
и передаёт вычисленный float в функцию с сохранённым элементом через RCX.
Это сильная зацепка для визуального перехода, а не готовая формула распознавания.

В каталоге есть два разных макета с ImageFader:

| Макет | Patch / base entry | Экспорт |
|---|---|---|
| WBP_FaderUI | 759 / 8067 | 3, NkImage |
| WBP_MediaUI | 789 / 8097 | 23, Image |

Четыре варианта сохранены в image_fader_widget_candidates с источниками,
хешами и родительскими цепями. Последующее исследование различило классы:
WBP_FaderUI наследуется от NkFaderUI, а WBP_MediaUI — от NkMediaPlayerUI.
Регистрация NkFaderUI и vtable связаны с разобранными методами настройки/сброса.
См. [FADER-CLASS.md](FADER-CLASS.md). Runtime Android этим не подтверждён.

## Таймер и остановка: границы знания

Диагностика `_StartTimer()` включает `CurrentTime Ticks == 0` и
`TimerHandle is not valid.`. В Start также есть диагностика недопустимой
длительности. Числа и fallback внутри этих ветвей не являются нормальными
таймингами игрового сценария и не переносятся в бот как паузы.

Reset перед очисткой очередей вызывает `0x144a7b5e0`, который обходит элементы
и вызывает другие helpers. Полная остановка таймера/отмена callback ещё
не доказана. Не утверждать «reset всегда отменяет анимацию и вызывает callbacks».

Native class связан с FaderUI в FADER-CLASS.md. Следующие задачи: полная
цепочка reset→stop, семантика флагов/повторов, reentrancy и сверка Android.
Телефон не затрагивался; новые нажатия или фиксированные ожидания не включены.

## Прямые вызывающие остановку, после коммита 40f3b64

`build-easing-stop-links.py` создаёт `code-clues/easing-stop-links.json`:
пять подтверждённых E8-вызовов `0x1445d2690`, пять корней / 11 фрагментов,
неразобранных кандидатов нет. Приняты только вызовы на декодированных границах.

| Вызывающий корень RVA | Вызов VA | Подтверждённое наблюдение |
|---|---|---|
| 0x45bf770 | 0x1445bf7b2 | Установка vtable, проверка флагов, очистка callback-объектов |
| 0x45c0440 | 0x1445c0488 | Аналогичная очистка; отдельная ветвь освобождения объекта |
| 0x45c4ab0 | 0x1445c4ae2 | Проверки флага, остановка и последующая обработка callback-данных |
| 0x45d10b0 | 0x1445d10cc | Обёртка остановки с очисткой handle+0x10 и границы+0xe0 |
| 0x45d33b0 | 0x1445d347a | Уже найденный путь остановки перед настройкой нового таймера |

Очистка callback-объекта вызывает его виртуальный слот+0x10, тогда как подготовка
payload перед **выполнением** callback использует слот+8, после чего следует вызов
самого сохранённого указателя. Эти операции не эквивалентны. Точные C++ имена
виртуальных методов пока неизвестны; по одному смещению не назначать им имена.

Прямой E8 из исследованного reset Fader в этот список не вошёл. Это не доказывает,
что reset никогда не останавливает таймер: возможны дополнительные/виртуальные
пути. Связь reset→stop остаётся `false` в отчёте, не заменяется догадкой.
