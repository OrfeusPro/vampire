## Уточнение составного runtime decoder, 19 октября 2026

Полный [native XOR и actual FString append](HEADLESS-GMC2-XOR.md) установили
пропуск нулевых результатов. Прежние 42 XOR fixtures и три pipeline examples
этого файла захватывали аргументы append; они не доказывали конечную FString
при zero outcome. Исторические отчёты сохранены без подмены.

decode_sdk_constants_string в общем sdk_constants.py теперь вызывает единственный
подтверждённый xor_gmc2_utf16_units после существующего unescape. Повторной
реализации escape/XOR нет. Старые локальные bounds 4096/1024 байта сохранены;
empty key теперь отклоняется даже для empty content. Результат — raw units,
не гарантия корректного Unicode/JSON. Исторический xor_sdk_utf16le сохраняет
pre-append units только как математическое преобразование/capture model,
а не конечную строку native decoder.

Два новых теста проверяют zero-outcome regression и все 18 новых native
output vectors через JSON escape → старый unescape → actual append XOR, включая
isolated surrogate и длинный source. Прежние native unescape evidence/tests
повторно используются; helper 1444f2670 уже был исследован, это не Base64.

Источник DECKEY по slot 28 и полная response chain всё ещё не доказаны.

| Источник | Подтверждённая связь |
|---|---|
| Constructor `0x1444bd970` | manager+`0xB0` инициализируется именем `DECKEY`, +`0x110` — `encConstants`, +`0x120` — `encSecretConstants` |
| Обработчик root `0x1444c8c60`, участок `0x1444c947b..0x1444c9492` | Через virtual slot `0x28` объекта из входного shared pointer запрашивается строка по имени manager+`0xB0`; результат помещается в локальную строку `[rbp-0x60]` |
| Вызов `0x1444c9587` → parser `0x1444f0e80` | Эта локальная строка передаётся в R8 как ключ; строка тела передаётся в RDX, выходной контейнер — в R9 |
| Parser `0x1444f0f2c..0x1444f0f45` | Имя manager+`0x110` передаётся extractor `0x1444e3bc0` |
| Extractor `0x1444e3e20` | Извлечённый участок строки передаётся в helper `0x1444f2670` |
| Parser `0x1444f0f58..0x1444f0f6e` | Результат helper и ключ передаются в ранее проверенный DecryptXOR `0x1444ddf50` |
| Parser `0x1444f12c5..0x1444f13c5` | Отдельно извлекается `encSecretConstants`, выполняется встроенный XOR и вызывается `0x1444ddc10` |

`DECKEY` в constructor — имя запрашиваемого значения, а не сам ключ.
Точный класс объекта с virtual slot `0x28` и семантика его метода пока не доказаны;
называть источник HTTP-заголовком только по расположению слота нельзя.
Реальное значение ключа не получено. Ветка `0x1444ddc10` дополнительно разбивает
строку и вызывает `0x14451d5c0`; её полная криптография ещё не восстановлена.

Extractor вручную ищет имя, границы значения, `null` и закрывающую кавычку.
Его устойчивость к форматированию/повторным ключам/неверному ответу не проверялась.
В общий код ручной поиск поля пока не перенесён. Все связи этой таблицы статические;
в эмуляторе выполнялся только helper и отдельный XOR, а не весь обработчик ответа.

## Проверенное преобразование строки

Helper `0x1444f2670..0x1444f2932` читает UTF-16 единицы без начальной кавычки,
останавливается на неэкранированной кавычке и разбирает escape-последовательности
`\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t`, `\uXXXX`.
Суррогаты сохраняются как 16-битные единицы. Это не Base64.

Unwind range включает таблицы переходов после RET. Они сохранены отдельно,
не выданы за инструкции и не скрыты через skipdata. Воспроизводится настоящий
цикл и switch. Только рост выходного массива заменён одной ограниченной
аллокацией до 2048 единиц. Импорт `powf` доказан через PE/IAT:
`api-ms-win-crt-math-l1-1-0.dll`; shim разрешает только `16**{0,1,2,3}`,
используемые для четырёх hex-цифр. Внешняя библиотека CRT не исполняется.

Проверено 43 корректных входа, включая оба регистра hex, NUL, суррогатную пару,
изолированный суррогат, все специальные escape и вход длиной 2048 единиц.
Семь дополнительных входов показывают границы: например, `abc\q` даёт только
`abc`, а необработанный перевод строки копируется. Ошибку native helper не сообщает.
Три искусственных JSON проходят оба native этапа: escape → XOR → исходные единицы,
в том числе с кириллицей и символом вне BMP. Это не ответы сервера игры.

Общий [sdk_constants.py](../../vampir-shared/vampir_core/sdk_constants.py) дополнен
`unescape_sdk_utf16le` и `decode_sdk_constants_string`. Вход — содержимое JSON-строки
в UTF-16LE без внешних кавычек, максимум 4096 байт. Выход — исходные UTF-16LE bytes;
дальнейший разбор JSON и проверка адресов остаются отдельными задачами.
Некорректные escape, необработанные кавычки и управляющие символы отклоняются
без вывода содержимого в ошибку. Эта политика намеренно строже native helper.
Если весь ответ уже разобран JSON-декодером, строка уже unescaped: повторно
применять этот шаг нельзя, нужен только `xor_gmc2_utf16_units` из gmc2_decode.py
для результата actual append. Прежний xor_sdk_utf16le моделирует raw XOR units.

Пять тестов проверяют provenance, все native результаты, три составных примера,
повторное исполнение 16 сценариев и строгие ограничения. Следующий шаг — доказать
класс и метод получения DECKEY, затем secret constants и привязку выходного
контейнера к `authTokenUrl`/`clientId`. `network_ready=false`.
