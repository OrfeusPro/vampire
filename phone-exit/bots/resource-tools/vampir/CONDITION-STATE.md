# Vampir: обновление контекста блокировок

Продолжение [CONDITION-PREDICATE.md](CONDITION-PREDICATE.md) и
[CONTENTS-LOCK-FIELDS.md](CONTENTS-LOCK-FIELDS.md). Проверены файлы Windows-клиента,
без чтения памяти процесса и без телефона. Названия ролей ниже выведены из
потребителей полей; оригинальные имена флагов не восстановлены.

## Как повторить

`python phone-exit/bots/resource-tools/vampir/build-lock-state-code.py`
создаёт `F:/PhoneExit Resources/Vampir/code-clues/lock-state-code.json`.
Вход — тот же EXE, SHA256
`c7552efd2125e7981945d3443cc1d70a41ac0a8a4cb42e7c77e0d40b4713dfc8`.
Проверяются 32 опорные инструкции, 15 unwind-фрагментов, один прямой вызов обновления
полей и значение 3 из native enum. Генератор сохраняет инструкции, байты,
файловые смещения и SHA фрагментов. Закреплён Capstone5.0.6.

Первичный поиск записей по смещениям дал много чужих объектов и стековых
переменных. Само совпадение+0x224 ничего не доказывает. В доказательства включены
только функции, связанные вызовами с ранее найденным контекстом и предикатом.

## Сброс и два флага

В `0x145cf3440` инструкция `0x145cf3464` записывает word1 в context+0x220.
В little-endian это одновременно задаёт byte+0x220=1 и byte+0x221=0.
Затем `0x145cf3470` обнуляет byte+0x222, а `0x145cf3477` обнуляет qword+0x224,
то есть оба dword уровней+0x224/+0x228. Следующий код очищает контейнеры.
Это нельзя трактовать как выставление готовности: оба проверяемых флага сброшены.

В `0x145ceb7e0` есть ещё явная запись 0 в+0x221 (`0x145ceb7fc`).
Перед пересчётом `0x145cf07f0` проверяет оба флага+0x221/+0x222 и при нуле
уходит в ранний выход. При двух ненулевых флагах вызывает `0x145cf5c50`
в `0x145cf083a`, до обхода таблиц и вызовов группового предиката.

## Входной массив разрешений

`0x145ced700` получает RCX=контекст, RDX=входной массив dword,
R8B=режим обновления, R9B=ещё один флаг (назначение пока неизвестно).
Происхождение массива и вызывающий косвенный обработчик не установлены:
называть функцию доказанным сетевым ответом нельзя.

- При R8B!=0 очищает count списка context+0x1b0 и копирует входной массив.
  Самоприсваивание проверяется отдельно. Входные дубликаты здесь не удаляются.
- При R8B==0 перебирает входные ID; если ID уже найден в списке, удаляет найденное
  вхождение со сдвигом хвоста, затем добавляет ID в конец. Это не удаление
  разрешения и не доказательство полного устранения любых старых дубликатов.
- После изменения списка в `0x145ced8f4` выставляет context+0x222=1.
  В следующих частях функции строятся связанные списки и записи.
- При обработке записей с SaveType==1 отдельно добавляет отсутствующий ID
  в context+0x1a0. Соответствие поля+0xe колонке SaveType доказано в V30.
  В исходной CSV все 269 SaveType=2, поэтому этот путь нельзя переносить на них
  как обычное правило сохранения.
- Позже `0x145cedc88` выставляет+0x221=1, и `0x145cedc90` вызывает
  `0x145cf07f0`. То есть факт получения списка и готовность к пересчёту разделены.

## Обновление полей уровней

`0x145cf5c50` перебирает числовые типы 0..10. Для каждого сначала вызывает gate
`0x145ce3dd0`; при false пропускает обновление. Реальные записи уровней находятся
в ветвях типов 0 (CharacterLevel) и 3 (GuildLevel):

| Поле контекста | Откуда записывается | Проверенные адреса |
|---|---|---|
| +0x224, CharacterLevel | Из результата 0x1455e19d0 с EDX=3, RCX берётся через объект 0x14558ee40 и поле+0x38 | вызов 0x145cf5d39, запись 0x145cf5d3e |
| +0x228, GuildLevel | При ненулевом результате 0x145d07af0 записывается 0; иначе читается dword+0x1b0 объекта от 0x1455b81a0 | записи 0x145cf5ca8/0x145cf5cbe |

Native enum содержит EAttributeType::Attribute3=3, а не символическое имя Level.
Это отдельное числовое совпадение; точная сигнатура getter и происхождение
ключа 3 ещё не доказаны. Функцию 0x145d07af0 также нельзя подписывать как
«нет гильдии» только по эффекту нулевого уровня: её контракт ещё не восстановлен.

Если gate запрещает обновление, старое поле здесь не обнуляется автоматически.
Это важно для будущего evaluator: свежесть значения и доступность типа нужно
проверять отдельно. Нельзя использовать кешированный уровень без состояния gate.

## Практический результат и следующий поиск

Связана цепочка входной список → два этапа готовности → пересчёт → обновление
уровней → групповые проверки. Она дополняет referenceRevision4, но пока хранится
в исследовательском отчёте: исполняемый evaluator бота не добавлен.

Следующее исследование нашло источник массива на уровне двух именованных
обработчиков результатов: [UNLOCK-RESULTS.md](UNLOCK-RESULTS.md). Путь к update
оказался двумя прямыми tail-jump, а не доказанным косвенным вызовом. Прежний
E8-поиск был недостаточен. Инициализация, setter и getter таблицы gate связаны
в [CONDITION-GATE.md](CONDITION-GATE.md); источники событий setter ещё неизвестны.
Остаются регистрация OnHandler, полный контракт guard, getter уровней/гильдии,
состояния квеста и Android. Полный сценарий прокачки всё ещё требует визуального
подтверждения текущего этапа и проверки на телефоне.
