# Vampir: клиентская проверка ContentsLockCondition

Статический разбор установленного Windows-клиента; телефон не использовался.
Читать после [CONDITION-TYPES.md](CONDITION-TYPES.md). Это восстановленная
клиентская функция, не готовый evaluator состояния персонажа и не серверный контракт.

## Источник и повторение

EXE: `ProjectRED-Win64-Shipping.exe`, SHA256
`c7552efd2125e7981945d3443cc1d70a41ac0a8a4cb42e7c77e0d40b4713dfc8`.

`python phone-exit/bots/resource-tools/vampir/build-lock-predicate-code.py`
создаёт `F:/PhoneExit Resources/Vampir/code-clues/lock-predicate-code.json`.
Нужны закреплённый Capstone5.0.6 и отчёт quest-graph/condition-types.json.
Проверяются хеш EXE, 30 опорных инструкций, таблица из 11 переходов и попадание
каждой цели на границу инструкции. Сохранены два отдельных диапазона кода,
девять unwind-фрагментов вспомогательных функций и исходные байты таблицы.

Поиск начался с кандидатов чтения byte[reg+0x10] и соседних сравнений с 10/11.
Сам по себе такой шаблон ничего не доказывает: три совпадения оказались очисткой
чужого контейнера. Проверяемая цепочка ниже основана на аргументах, полях и переходах.

В конце диапазона функции находится таблица RVA `0x145cda480..0x145cda4ac`.
При линейном дизассемблировании её байты могут выглядеть как инструкции.
Генератор отделяет их от кода `0x145cda340..0x145cda480` и проверяет цели отдельно.
Это правило нужно сохранять при дальнейшем разборе других switch.

## Функция одного условия

Адрес `0x145cda340`. На входе DL=тип, R8=Value1, R9=Value2, RCX=контекст.
Выход — AL. Поля и передача аргументов совпали с ранее разобранным загрузчиком.

Сначала тип 11 возвращает true без обычного dispatch. Это наблюдение для данной
функции, не основание называть 11 символическим Max. Для остальных типов вызывается
`0x145ce3dd0`: при false результат всего условия false. Gate проверяет два флага
контекста+0x221/+0x222 и таблицу по типу; имена/источники флагов пока неизвестны.
Отрицательный gate нельзя заменять проверкой только числового значения.

После gate тип больше 10 возвращает false; остальные идут по таблице:

| Тип | Имя из конвертера | Ветвь | Подтверждённые операции после gate |
|---:|---|---|---|
| 0 | CharacterLevel | 0x145cda397 | Value1 <= sign-extended dword[context+0x224], unsigned setbe |
| 1 | CompletedQuest | 0x145cda3a9 | Value1 передан в 0x145de21b0, результат AL возвращён |
| 2 | CompletedQuestTask | 0x145cda3b6 | Value1 передан в 0x145de2250, результат AL возвращён |
| 3 | GuildLevel | 0x145cda3c3 | Value1 <= zero-extended dword[context+0x228], unsigned setbe |
| 4 | EnterArea | 0x145cda3d1 | Младшие 32 бита Value1 переданы в 0x1456ab4f0 |
| 5 | EngravingId | 0x145cda47a | false |
| 6 | AdditionalSlotRarity | 0x145cda47a | false |
| 7 | EngravingAdditionalRarity | 0x145cda3da | Объект по младшим 32 битам Value1; проверки наличия и ещё один AL; затем Value2 <= byte результата, unsigned setbe |
| 8 | GuildJoined | 0x145cda424 | Проверки глобального объекта: qword+0x1f0 против глобального значения и byte+0x1e8; точные имена состояния неизвестны |

Имена CharacterLevel/GuildLevel подтверждены конвертером и dispatch. Источник
значений полей уровней и их актуализация ещё не прослежены. Псевдокод с обычными
Python int без учёта расширений/знаков может отличаться от машинного сравнения.
Для ветвей 5/6 результат false относится к этой версии и функции клиента;
нельзя объявлять эти типы несуществующими или серверно запрещёнными навсегда.

## CompletedQuest — больше, чем поиск ID

`0x145de21b0` сначала сравнивает Value1 с sign-extended глобальным dword;
при совпадении возвращает true. Значение/назначение глобального sentinel не установлено.
Затем получает запись квеста; при её отсутствии false. Флаг записи+0x30
выбирает разные пути: текущий квест или поиск в другом состоянии.
В одном пути сравниваются ID, а при равенстве проверяется byte состояния==5;
при разных ID используется signed setg. Значение 5 пока не названо reflected enum.
Поэтому таблицы CSV и имя CompletedQuest недостаточны для вычисления результата.

`0x145de2250` для CompletedQuestTask обращается к записи задачи и её квесту,
затем к текущему/сохранённому состоянию. Сравнения включают signed setl и состояние 5.
Некоторые ветви отсутствующих записей возвращают true. Не переносить сюда
правило «записи нет → всегда false» из другого helper.

## Предикат группы и ранние исключения

`0x145cf2dc0` получает контекст и объект блокировки. В обычной ветви он берёт
значение block+0x20 и через `0x1458de420` получает массив условий группы.
Accessor использует менеджер `0x1458e69e0`, шаг записи 32 и значение записи+8;
это соответствует структуре индекса из V28 (разница 8 у базового адреса менеджера).
Поле block+0x20 теперь отдельно связано с ContentsLockConditionGroupId:
[CONTENTS-LOCK-FIELDS.md](CONTENTS-LOCK-FIELDS.md). Там же подтверждены SaveType
в+0xe, Id в+8 и пять прямых вызовов предиката.

Цикл `0x145cf2e80..0x145cf2ea2`:

1. Загружает указатель условия, тип+0x10, Value1+0x18 и Value2+0x20.
2. Вызывает `0x145cda340`.
3. При false сразу возвращает false; при true идёт к следующему указателю.
4. После последнего условия возвращает true. Отсутствующая или пустая группа
   в этой ветви также даёт true.

Это **AND с коротким замыканием для обычного клиентского пути**. До него есть
важные ветви, которые нельзя удалить:

- Сначала вызывается `0x145cf33c0` с типом 10. Helper ищет такой тип в массиве;
  присутствие ForcedLock возвращает false из предиката до последующих разрешений.
- Если block+0xe==1, проверяется список context+0x1a0/count+0x1a8;
  совпадение block+8 даёт true. Название этого режима отдельно не восстановлено.
- Ещё один список context+0x1b0/count+0x1b8 при совпадении block+8 даёт true.
- Только после этих ветвей выполняется обычный цикл AND.

Соседняя функция `0x145ce2040` тоже вызывает предикат условия в цикле и после
первого false выбирает ветвь формирования текста по типу. Её возврат — строковый
результат, а не boolean всей группы; не смешивать её с `0x145cf2dc0`.

## Что осталось и что меняется для бота

Найден реальный клиентский dispatch и обычный AND-путь с исключениями.
Остаются источник и обновление gate/уровней/списков разрешений, семантика состояний
квеста, назначение вызывающих функций и Android. В referenceRevision4 справочника
добавлен отдельный clientPredicateReference с доказанным клиентским путём;
общая неопределённость результата для персонажа сохранена. Универсального
evaluator нет. Связь полей и процедура соединения — в CONTENTS-LOCK-FIELDS.md.

Обновление флагов, входного списка разрешений и кешированных уровней теперь
частично связано в [CONDITION-STATE.md](CONDITION-STATE.md). В частности,
пересчёт сначала обновляет уровни, но только для разрешённых gate типов;
само происхождение gate и входного массива ещё не установлено.
