# Шаблоны устройств и подключение

Панель аккаунтов строится вокруг таблицы. Нажатие на аккаунт, персонажа, сервер,
шаблон или состояние открывает соответствующий попап. Настройки аккаунта
разделены на вкладки; обзор устройства и его редактирование разделены. Фоновые
обновления не сохраняют форму и не сбрасывают введённые поля. Фильтры под колонками
применяются совместно с поиском; общий сброс очищает их. Нажатие на заголовок
колонки сортирует строки; повторное нажатие меняет направление. Серверы и имена
с числами сравниваются естественным порядком. По умолчанию аккаунты на устройствах внизу; тип Бот — в первой группе. Номер
аккаунта постоянен и не меняется при сортировке или фильтрации. Типы
«Не задействован» и «Не использовать» находятся отдельно от рабочих устройств.
Первый исключён из общего запуска, второй отключает все новые операции аккаунта.
Пароли скрыты в попапе аккаунта; экспорт всей таблицы с паролями остаётся явным.

## Одно устройство на два места

Шаблон хранится отдельно в локальной SQLite: постоянный ID, название, имя для
регистрации, аппаратные параметры, три независимых ключа, ревизия и происхождение.
Аккаунт хранит ссылку на шаблон. Пара получает общие параметры / ключи / имя,
а сервер, персонаж, пароль, способ входа и сетевой маршрут остаются у аккаунта.
Лимит — два аккаунта / два одновременно выбранных персонажа. Это не лимит всей
истории персонажей, когда-либо существовавших у этих аккаунтов. Ограничение
соблюдается в SQLite-транзакции при назначении и сохранении, включая гонку
двух заявок на последнее место. Занятый шаблон недоступен для третьего аккаунта.

Три ключа заполняются при создании устройства один раз, сохраняются и показываются
в попапе скрытыми до явного включения. При уходе из окна снова скрываются.
Ключи различных шаблонов не пересекаются. Изменение ключей — отдельная кнопка
в режиме редактирования. Изменение шаблона затрагивает оба его аккаунта;
во время работы любого из них редактирование заблокировано. Старый fallback
аккаунта и исторические привязки персонажей сохраняются, но назначенный общий
шаблон имеет приоритет при новом запуске. Пароли и привязки DPAPI не заменяются.

Имя для регистрации записано в самом шаблоне и общее на два места. Генератор
использует формат `DESKTOP-XXXXXXX`: семь случайных заглавных букв / цифр,
проверка уникальности среди шаблонов. Это привычная форма имени Windows;
[пример производителя](https://www.dell.com/support/kbdoc/en-us/000137111/computer-name-shows-as-desktop-xxxxxx-on-dell-systems-that-ship-with-windows-10).
Имя не меняется при входе и не переименовывает Windows ПК. URL официальной
регистрации получает `deviceName` из этого поля вместо `socket.gethostname()`.
Уже зарегистрированные имена на сервере автоматически не переименовываются.

Генерация использует наблюдённый CPU, Windows, RAM, GPU, часовой пояс и локаль
текущего ПК с отдельными ключами для каждого шаблона. Если SMBIOS не содержит
модель производителя, шаблон явно задаёт общее `Desktop PC`; это не модель,
наблюдённая в прошивке. Встроенные вымышленные Intel / AMD / laptop-примеры убраны.
Команда генерации назначает только ещё не назначенные аккаунты: сначала свободные
места, затем новые устройства. Повтор сохраняет устройства и ключи.

При изменении ключей, имени регистрации, аппаратных данных или маршрута прежнее
подтверждение не относится к новой конфигурации. Свежая верификация записывается
по fingerprint устройства и маршрута конкретного аккаунта. История старой очереди
сохраняется и не выдаётся за подтверждение нового шаблона. Рабочие типы устройства —
Телефон, ПК, UgPhone, LdCloud и Бот. У каждого свой цвет; резерв и запрет
использования выделены отдельно. Тип меняется в попапе аккаунта,
отображается в таблице и не переключает Windows-протокол на Android.

## Наблюдение этого ПК

Попап «Этот ПК» читает CPU через существующий SHA-проверенный CPUID reader,
версию для SDK через GetVersionExW текущего процесса, остальные характеристики
через Windows CIM. Отдельно показана версия ОС. Недоступные поля не угадываются.
При открытии панели выполняется одно чтение; повтор — кнопкой обновления.
Наблюдение не записывает значения в аккаунты и не меняет настройки Windows.

«Создать шаблон на этой основе» заполняет новый шаблон и создаёт отдельные ключи.
Его сохранение и назначение аккаунту — отдельные действия. После назначения
необходим новый вход / верификация устройства; просмотр или генерация не
выполняют авторизацию в игре.

## Используемые поля

| Поле | Применение |
| --- | --- |
| NID deviceKey | NID URL и отдельный каталог WebView по digest привязки |
| SDK deviceKey | SDK request, metadata лобби / игры |
| nmDeviceKey | NID, SDK, лобби и Version / Login |
| Имя регистрации | `deviceName` официального окна регистрации устройства |
| Windows major/minor/build/product type/suite mask | NID osVersion, Version |
| CPU vendor / brand | Version; I_NMCPU из тех же значений |
| I_DeviceModel / I_NMRAM / I_NMVGA | Явные дополнительные metadata |
| I_TimeZone / I_LanguageCD | Metadata, отдельно от session clock / language byte |
| SOCKS port | Маршрут конкретного аккаунта; прямой fallback отсутствует |

IP и страна выхода берутся из свежей GMC2 через выбранный маршрут. Страна аккаунта
берётся из свежего NID / SDK ответа. Шаблон их не подменяет. Google-верификация
пока поддерживает прямой выход ПК. Android ID, MAC, SIM, оператор, browser headers,
токены и пакетные sequence в шаблоне не изобретаются. Полный список полей и
границы — в [диагностике входа](ENTRY-DIAGNOSTICS.md).

## Проверка и обновление

Реестр `research-checks.json`, source check `sdk-runtime-launcher-11316` текущего
SHA и группа `account-verification` учитывают хранилище шаблонов, его потребителей,
официальную регистрацию и интерфейс. Новый тест зарегистрирован в MODULES и
ровно одной группе; общая зависимость добавлена во всех её потребителей.
Проверены capacity / гонка, идемпотентная генерация, общая identity пары,
сохранение паролей, rollback, fingerprint и отсутствие игровых команд при просмотре.
SDK и готовые native-доказательства переиспользуются; новый native разбор не нужен.

Локально назначены 30 аккаунтов на 15 устройств после резервной копии. Новые
custom identity / аппаратные metadata ещё не приняты живым сервером; прежняя
Google-верификация на ключах текущего ПК не подтверждает их. Программная проверка
формы / URL и fixtures отдельно от фактического онлайн-результата.
