# Почта и постоянное устройство Vampir

Обновлено 19 октября 2026. Это локальный реестр бота, а не формат хранения игры.
По указанию пользователя основной аккаунт — ранее созданная тестовая почта.
Её фактическая запись создана в `.local/accounts.sqlite3`: основной профиль
типа `real`, идентификаторы ещё не получены, подтверждение `unknown`.
Адреса и значения устройств хранятся в локальной базе, не в общей документации.

## Общая таблица

| Поле | Назначение |
| --- | --- |
| email | Один адрес — одна постоянная запись; локальная нормализация регистра |
| profile_id | Случайный UUID записи бота, не fingerprint и не поле протокола игры |
| kind | `real` — для наблюдаемого устройства; `planned` — будущий профиль без выдуманных данных |
| is_main | Не более одного основного аккаунта в базе |
| device_key | Отдельное значение SDK deviceKey; пока пусто |
| nm_device_key | Отдельное значение SDK nmDeviceKey; пока пусто |
| identity_source | Происхождение наблюдения: устройство, метод, версия и дата; без секретов |
| confirmation | `unknown`, `required` или `confirmed` |
| confirmation_evidence | Краткая ссылка/пометка о ручном подтверждении, без кода и содержимого письма |
| updated_at | Время последнего изменения в UTC |

Реализация: [device_registry.py](../vampir-shared/vampir_core/device_registry.py).
SQLite и Python stdlib не требуют внешнего сервера. Формат переносим;
Android-адаптер и защита данных на Android ещё не реализованы.
База — локальный открытый текст, не защищённое хранилище секретов.
Права доступа и резервную копию базы должен обеспечивать владелец профиля ОС.
Пароли, токены, OTP, письма и ключи почтового ящика в неё не записывать.
Каталог `.local/` исключён из Git, включая SQLite journal/WAL-файлы.

## Устойчивость и подтверждение

Повторное добавление той же почты с тем же типом возвращает прежний профиль.
Смена типа/основного флага существующей записи и замена полученных идентификаторов
отклоняются. Идентификаторы не генерируются этим модулем. После перезапуска и
еженедельного обновления данных игры база и привязки сохраняются.
Перенос устройства требует отдельного будущего процесса, а не удаления записи.

`record_real_identity` сохраняет явно переданные наблюдаемые deviceKey и
nmDeviceKey вместе с источником. Вызов не доказывает подлинность этих данных.
`identity_recorded` означает лишь заполненность записи, не готовность входа.
`require_confirmation` фиксирует запрос нового подтверждения, даже если раньше
устройство было подтверждено. `record_confirmation` требует заполненной identity
и явной пометки об основании; сам письма и сервер не проверяет.

Будущий login runner должен при `required` прекращать автоматические попытки
входа до завершения штатного подтверждения. Сейчас runner и распознавание
серверного challenge отсутствуют: реестр сам не управляет авторизацией.
`unknown` не означает ни разрешение, ни запрет со стороны сервера.

## Что известно из данных клиента

Native SDK sign-in передаёт **два отдельных поля** deviceKey и nmDeviceKey:
[цепочка функций, версия EXE, SHA256 и воспроизведение](../resource-tools/vampir/HEADLESS-SDK-SIGN-IN.md).
Email web flow также передаёт deviceKey и контекстные headers:
[JS источники и границы](../resource-tools/vampir/HEADLESS-NID-EMAIL.md).
Windows storage/GUID fallback разобраны статически, default GUID formatter
исполнен на synthetic fixtures: [source/SHA](../resource-tools/vampir/HEADLESS-DEVICE-IDENTITY.md).
Связь с физическим устройством, полный active storage lifecycle,
дополнительные характеристики и серверная политика привязки пока не доказаны.
Нельзя заменять оба поля одним UUID или считать любой Android ID их значением.

Отдельные стабильные профили для остальных почт запланированы. Создание виртуальных
идентификаторов, их принятие сервером и влияние ограничений входа не проверены.
Подтверждение устройства по почте пока известно из сообщения пользователя;
серверная схема ошибок/challenge и повторной проверки ещё не найдена.
