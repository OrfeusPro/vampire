# Автоматический сборщик интерфейса Vampir

Общая цель: постепенно дополняемый сборщик, который восстанавливает интерфейс
игры по данным клиента. Карта заменяет игровой мир; сгенерированные HUD, окна,
меню и попапы располагаются поверх неё. Прежний прототип служит стендом и
проверочным результатом. [Постоянные задачи UI-22](UI-TASKS.md) дополняют,
а не отменяют проверки каждого окна, оформления, событий и версий.

## Конвейер

1. Проверенные извлечённые каталоги, полный SHA источников и явный baseline.
2. Промежуточная схема: ресурс / вариант → exports → локальные slots → вложенные
   WBP → геометрия / оформление / состояния / события. Неизвестные поля явные.
3. Общие компиляторы Canvas, Overlay, Box, SizeBox и остальных типов, затем
   библиотека оригинальных компонентов и их вариантов. Поддержку расширять
   постепенно; не копировать исправления по отдельным окнам.
4. Общий рендерер подключает схему к модели данных и адаптеру действий.
   Подтверждённые native события, локальные демодействия и транспорт различаются.
5. Сборка создаёт неизменяемый snapshot, отчёт покрытия, изменения относительно
   baseline и список затронутых потребителей; проверки геометрии, стилей,
   событий и визуального совпадения выполняются раздельно.

Ручное исключение должно иметь причину, источник, полный SHA и незакрытую
проверку. Нельзя скрывать неизвестный widget, угадывать brush по имени PNG,
выбирать вариант из другого архива или подменять исходную функцию демофункцией.
Извлечённый cooked-каталог не содержит автоматически всего поведения игры;
недостающие свойства / привязки требуют дополнительных декодеров и проверок.

## Уже доступная основа

Команда из корня репозитория:

```powershell
python -X utf8 phone-exit/bots/resource-tools/vampir/build-ui-prototype.py
```

Существующий сборщик сохраняет полные источники, оригинальные изображения,
декодированные slots, отдельные схемы размещения и состав общих компонентов.
Новый шаг `ui_composition_graph.py` строит `composition-graph.json` для всех
каталогизированных вариантов. Узел сохраняет путь / catalog file / SHA, состав
типов контролов; ребро — export / SHA контрола и кандидатов вложенного класса.
Даже единственный кандидат не означает, что активный runtime вариант выбран.
Проверка snapshot повторно строит граф из опубликованных `windows/*.json`.

С явным `--baseline <путь к manifest.json>` сборка также создаёт рядом со snapshots
отдельный `*-to-*-composition.json`: добавленные, удалённые, изменённые варианты
и транзитивный список повторной проверки. Обход учитывает оба графа, все варианты
и циклы; это консервативный список кандидатов, а не подтверждение совместимости.
Отчёт сравнения хранится снаружи неизменяемого snapshot, чтобы другой baseline
не менял его содержимое. Исторические версии граф не объединяет в один UI.

Самостоятельная проверка уже опубликованных наборов:

```powershell
python -X utf8 phone-exit/bots/resource-tools/vampir/ui_composition_graph.py --snapshot '<NEW_SNAPSHOT>' --baseline '<OLD_SNAPSHOT>' --output '<REPORT_OUTSIDE_SNAPSHOTS>.json'
```

Граф строится при сборке, не в каждом окне и не каждый кадр. Рендерер должен
загружать только открываемые схемы, использовать общие неизменяемые ресурсы
и независимое состояние каждого бота. Реальные 50 окон требуют отдельного замера.

## Локальные схемы и первый потребитель

`ui_layout_schema.py` компилирует каждый вариант в `layout-schemas/<SHA>.json`.
`layout-schema-index.json` связывает путь и catalog file со схемой и её SHA;
`component-layouts.json` содержит небольшой список явно выбранных вариантов
общих компонентов. Ни BlueprintGeneratedClass, ни первый узел без родителей
не считаются автоматически видимым корнем окна.

Схема сохраняет контролы и их export SHA, исходные слоты с provenance,
входящие / дочерние связи, SizeBox constraints, container_geometry,
недекодированные слоты и исходные ограничения. Узлы анимации / WidgetTree
сохраняются как metadata. Несколько родителей, висячие ссылки и циклы дают
диагностику; defaults, visibility, SafeZone, desired size, transforms,
оформление и события остаются явно неизвестными там, где не восстановлены.

Скомпилированы 2376 схем: 117916 узлов и 72153 декодированных слота.
43 висячие ссылки в 29 вариантах и 2783 исключённых исходным декодером слота
учтены как открытые пробелы (UI-22.15). Verifier воспроизводит каждую схему
из опубликованного исходного варианта и сверяет байты и счётчики.

Первый runtime потребитель — общий статус персонажа. `layout-schema.js`
проходит текущие входящие Canvas slots до явно выделенного корня, рассчитывает
рамки общим Geometry.canvas и не использует записанные вручную цепочки.
HUD, коллекции и магазин получают одни результаты из общего компонента.
Остальные контейнеры пока возвращают `unsupported_container`, а неизвестный
AutoSize / desired size не превращается в нулевой размер. Для статуса явная
временная политика принимает пропущенный AutoSize за false и сохраняет это
в diagnostics; native inherited defaults ещё требуют проверки (UI-22.14).

Нормальный запуск загружает только выбранную схему статуса (около 55 КБ),
а не весь каталог схем около 100 МБ. Расчёт локальных
рамок кэшируется экземпляром библиотеки; масштабирование применяет общий
CSS-коэффициент, без обхода всех схем на кадр. Полная генерация DOM и стилей
по схемам следующих окон ещё не завершена — UI-22.05–07 остаются открытыми.

## Готовность

Граф связей — первый шаг, не полная автогенерация. Готовое окно должно собираться
из схемы общими правилами, иметь проверенные источники, геометрию и оформление,
событийный контракт, визуальную сверку и результат проверки в UI-WINDOW-TASKS.
Весь сборщик готов после воспроизводимой пересборки согласованного набора всех
обязательных окон с отчётом unknowns и проверками обновления клиента.
