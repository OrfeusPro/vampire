# Разовое сравнение скорости 0.4.2

Опциональная возможность control hello: `download-probe-v1`.
ПК отправляет `{type:"download-probe",id:<16 hex>}` только по команде оператора.
Android принимает максимум один замер на WebRTC-соединение.
Фиксированный HTTPS адрес: `https://speed.cloudflare.com/__down?bytes=5000000`.
Загрузка через Wi-Fi Network без LTE, редиректов, отключения TLS или сохранения
содержимого; адреса DNS проверяются как публичные. Максимум 5 МБ и 60 секунд.
Остановка соединения отменяет HTTP-запрос.

Ответ: `{type:"download-probe",id,bytes,elapsedMs,success}`.
Только размеры и монотонное время, без IP, содержимого или пользовательских URL.
ПК проверяет id ожидаемого запроса, границы чисел и тип результата. Heartbeat
продолжается: загрузка выполняется в IO-пуле, ответ сериализуется в signals.
Следом ПК скачивает такой же объём с того же адреса через SOCKS/WebRTC.
Измерения последовательные; отношение скоростей является диагностикой, не
доказательством единственной причины. Прямой замер не измеряет uplink телефона;
туннель зависит также от него, маршрута до ПК и реализации транспорта.

0.4.3 добавляет `upload-probe-v1`: команда/ответ `upload-probe`, одноразовый
POST 5 МБ синтетических данных на фиксированный Cloudflare `/__up`.
Один upload и один download на соединение, последовательно; ограничения те же.
`open` TCP может задавать `frameSize` 1024, 4096 или 16384, только размер порции
чтения на телефоне; окно 262144 и максимальный кадр 16384 сохранены.
PHONE_EXIT_TRANSPORT_PROBE=1 включает только агрегаты SCTP на ПК: счётчики,
повторы, скачки TSN, размеры окон. Скачок TSN не доказывает потерю пакета.

0.4.4: hello limits.tcpWindow=1048576 сообщает начальное окно выхода Android→ПК
1 МиБ; ПК принимает его только в этом точном размере, иначе прежние 262144.
PC→Android остаётся 262144. Максимальный кадр не меняется, очереди ограничены
окном, credit подтверждает только запись в локальный TCP. Предыдущие APK сохраняют
прежнее окно. PHONE_EXIT_TEST_LATENCY_MS — только диагностическая искусственная
задержка исходящих SCTP пакетов ПК; не включать в обычном запуске.

## Результаты диагностики 0.4.3–0.4.4

Удалённый Samsung SM-G990B 0.4.3: прямой upload 5 МБ за 0,600 с,
около 66,7 Мбит/с. Значит, быстры оба направления между телефоном и Cloudflare;
это не измерение пути телефон→ПК. Через туннель с кадром 16384: 26,296 с,
около 1,52 Мбит/с; 4096: 30,455 с, около 1,31; 1024: 34,232 с, около 1,17.
Уменьшение кадра не подтвердило улучшения, обычный размер оставлен 16384.
Задержанные SCTP ACK 20 мс дали 36,797 с и heartbeat до 7925 мс;
объединение credit с порогом 16 КиБ/таймером 10 мс — 31,792 с.
Оба прототипа удалены из клиента как не подтвердившие пользу.

USB vivo, искусственная задержка исходящих SCTP пакетов ПК 350 мс:
окно 256 КиБ — 5 МБ за 18,571 с, около 2,15 Мбит/с;
окно 1 МиБ — 13,913 с (2,88 Мбит/с) и 7,933 с (5,04 Мбит/с).
Результат колеблется; это предварительная проверка направления оптимизации.
APK 0.4.4 собран, lint пройден, установлен на USB vivo. HTTPS, UDP DNS/STUN
и 11 локальных тестов прошли, включая 3 параллельных бинарных TCP потока
по 700000 байт с half-close через настоящий WebRTC и окно 1 МиБ.
Удалённый Samsung 0.4.4 пока требует обновления и замера. Системный TUN,
Discord и загрузка конкретной игры этими тестами не проверены.

Внешние материалы для дальнейшей проверки:
- RFC 8831: общие ограничения SCTP и взаимное влияние каналов,
  https://datatracker.ietf.org/doc/html/rfc8831
- Похожее наблюдение падения SCTP throughput при росте RTT в другой библиотеке,
  https://github.com/pion/sctp/issues/218 (не доказательство причины в Werift).
- Нативный транспорт для контрольного сравнения на Windows,
  https://github.com/murat-dogan/node-datachannel.

## Нативный транспорт Windows 0.4.4

Установлен закреплённый node-datachannel 0.33.4 с Windows x64 binary и lock-файлом.
Сначала отдельный адаптер проверен на USB vivo: 5 МБ за 0,875 с (~45,7 Мбит/с),
HTTPS и UDP DNS/STUN. Затем Samsung 0.4.4, два замера: 6,846 и 6,453 с,
~5,84 и 6,20 Мбит/с; heartbeat 331–560 и 339–446 мс.
Werift с тем же Samsung 0.4.4: 33,054 с (~1,21 Мбит/с), heartbeat 330–1267 мс.
Это последовательные сравнения, условия маршрута могли меняться.

Нативный транспорт выбран по умолчанию в src/main.js. src/native-peer.js сохраняет
границы сообщений, отдельную ненадёжную UDP передачу, credit/backpressure,
закрытие каналов, проверку DTLS fingerprint и только STUN без relay.
Исходящий сокет привязывается к физическому IPv4, выбранные и объявленные
remote ICE адреса передаются существующей маршрутизации TUN. Сбор ICE ограничен
15 секундами; сырые логи библиотеки отключены. PHONE_EXIT_TRANSPORT=werift оставлен
для явного контрольного сравнения, автоматического переключения при ошибке нет.

Повтор после переноса в основной main.js: Samsung 5 МБ за 6,926 с (~5,78 Мбит/с),
heartbeat 332–631 мс; HTTPS, UDP DNS/STUN прошли. 13 тестов (оба транспорта для
бинарных параллельных потоков/half-close/UDP/закрытия) и оконный SelfTest прошли.
Обновлять Android дополнительно не нужно. Проверка системного TUN, Discord,
лаунчера и долговременной нагрузки на этом транспорте остаётся необходимой.

## Протокол диагностики 0.4.5

`flow-probe-v1` в hello разрешает open TCP с `sendBuffer`: 262144 (обычный),
524288 или 1048576 байт, только порог bufferedAmount телефона. Credit/window
Android→ПК остаётся 1048576, максимальный кадр 16384, PC→Android 262144.
`flowProbe:true` включает только для этого тестового TCP счётчики bytes/frames,
creditWaits/bufferWaits/waitMs/maxBuffer в памяти текущего соединения.
Команда control `{type:"flow-probe",id:<16 hex>}` возвращает один агрегат за
соединение с тем же id. Нет адресов, содержимого или постоянной телеметрии.
Суммарное ожидание нескольких потоков может перекрываться по времени.
ПК принимает только ожидаемый id и неотрицательные безопасные целые числа.
Без объявленной возможности остаётся прежний порог; параметры меняются только
явной диагностической командой до подтверждения улучшения.

0.4.6 добавляет `limits.maxTcpWindow=4194304`: при наличии этого лимита ПК может
передать в TCP open `tcpWindow` 1048576/2097152/4194304, начальный credit и граница
приёма ПК совпадают. Без параметра остаётся 1048576. Также open `receiveBuffer`
0 (настройки ОС) или 1048576 просит SO_RCVBUF на телефоне до TCP connect.
При диагностике агрегат `socketBuffer` сообщает максимальный фактический размер
через getReceiveBufferSize, а не предполагает принятие настройки ОС.
Порог sendBuffer не больше 1048576, кадр 16384. После сравнений обычный клиент
выбирает окно 2097152 и sendBuffer 524288 для APK с этим объявленным лимитом.
Для старых APK остаются прежние параметры. SO_RCVBUF по умолчанию задаёт ОС.

## Сравнение окон и очередей 0.4.6

Удалённый Samsung SM-G990B, последовательные замеры одного телефона. Один поток
скачивает 20 000 000 байт; четыре — по 5 000 000, тот же суммарный объём.
Данные curl направляет в NUL. Во время загрузки идут heartbeat и UDP DNS-запросы
раз в секунду. Отсутствующий DNS-ответ не доказывает потерю именно UDP-пакета.
Результаты — агрегаты в игнорируемой .tools/load-comparison.json.

| Окно / очередь телефона | Один поток, Мбит/с | Четыре потока, Мбит/с |
| --- | ---: | ---: |
| 1 МиБ / 256 КиБ, прежние | 11,075 | 20,328 |
| 1 МиБ / 1 МиБ | 11,270 | 18,859 |
| 4 МиБ / 1 МиБ, запрос SO_RCVBUF 1 МиБ | 15,267 | 19,064 |
| 4 МиБ / 1 МиБ, SO_RCVBUF от ОС | 15,352 | 20,313 |
| 2 МиБ / 512 КиБ, SO_RCVBUF от ОС | 15,351 | 20,266 |
| Повтор прежних параметров на APK 0.4.6 | 10,102 | 19,704 |
| Финальный обычный запуск 2 МиБ / 512 КиБ | 15,392 | 21,221 |

Выбран вариант 2 МиБ / 512 КиБ: скорость сравнима с большим окном при меньшей
границе очередей. В этом замере heartbeat 325–557 мс; UDP-ответы 11/11 и 8/8.
Это увеличение примерно на 39% относительно первого длинного замера одиночного
потока; маршрут меняется, поэтому результат не является гарантированной скоростью.
Короткие предыдущие замеры 5 МБ нельзя напрямую сравнивать с длинными 20 МБ.

Увеличение только sendBuffer, TCP_NODELAY, объединение credit 64 КиБ/20 мс,
меньший кадр, native SACK 5 мс не дали устойчивого выигрыша. Native SCTP буферы
4 МиБ ухудшили параллельную загрузку до 4,155 Мбит/с и RTT до 3988 мс.
Эти прототипы удалены. Размер кадра 16384 и стандартные настройки SCTP сохранены.
Запрос SO_RCVBUF не нужен: Samsung фактически вернул 458752 байт вместо
запрошенного 1048576; с настройкой ОС — 1048576. Нельзя считать запрос принятым
без проверки getReceiveBufferSize.

APK 0.4.6 собран, lint: 0 ошибок, 11 предупреждений. Установлен поверх vivo,
Samsung обновлён пользователем. USB vivo: 20 МБ 72,786 Мбит/с, четыре потока
77,652 Мбит/с с диагностическим окном 4 МиБ; это текущая локальная сеть.
13 npm-тестов прошли: реальный native↔Werift WebRTC, три бинарных потока по 5 МБ
с выбранным окном 2 МиБ, half-close, UDP и закрытие после потери канала.
Оконный SelfTest запуска/остановки/перезапуска/закрытия также прошёл.
Финальный запуск без диагностических переопределений окна/очереди подтвердил
выбранные параметры: один поток 20 МБ за 10,395 с, четыре за 7,540 с.
Heartbeat 315–487 мс, UDP-ответы 11/11 и 8/8; HTTPS, UDP DNS/STUN и TCP-цепочка
sing-box→SOCKS→WebRTC прошли. Это проверка цепочки без установки системных маршрутов,
а не новый полный TUN-тест. Сравнение с непосредственно предшествующим повтором
прежних параметров: +52% для одиночного потока, +8% для четырёх.
Пользователь подтвердил, что после 0.4.4 звук Discord больше не пропадает.
Видео, конкретная загрузка игры и длительная работа более 30 телефонов ещё
не подтверждены этими тестами.

## Число одновременных загрузок

Диагностический probe принимает PHONE_EXIT_DIAG_STREAMS как список из 1/4/8/16
(до четырёх разных значений), PHONE_EXIT_DIAG_TOTAL_BYTES — 20000000 или 32000000
байт на фазу. У каждой фазы отдельный диапазон UDP transaction id, чтобы поздние
ответы предыдущей фазы не смешивались с текущими. Без параметров остаётся
прежняя проверка 1/4. Эти параметры не заставляют обычные приложения создавать
дополнительные HTTP-запросы и не меняют SOCKS/VPN лимиты.

Сам продукт уже допускает 128 TCP и 64 UDP-ассоциации. Увеличение этого лимита
не ускоряет проверенные 4–16 потоков. DataChannel внутри одной SCTP-ассоциации
делят congestion window: https://datatracker.ietf.org/doc/html/rfc8831#section-5.
Это объясняет, почему число каналов не обязано пропорционально увеличивать скорость;
само по себе не доказывает, что именно SCTP ограничивает этот конкретный маршрут.

Samsung 0.4.6, обычные параметры 2 МиБ/512 КиБ, одинаковые 32 МБ на фазу:

| Потоки | Порядок 4→8→16, Мбит/с | Порядок 16→8→4, Мбит/с |
| --- | ---: | ---: |
| 4 | 18,817 | 13,348 |
| 8 | 22,577 | 22,409 |
| 16 | 22,600 | 19,084 |

8 потоков показали близкие результаты в двух запусках; устойчивый выигрыш от 16
не подтверждён. У 4 заметная вариация, поэтому нельзя приписывать всю разницу
числу потоков. Heartbeat во всех фазах 315–772 мс. UDP DNS ответы 37/38 в первом
запуске, 46/46 во втором. Один отсутствующий ответ не доказывает потерю пакета.
Во втором запуске 8 потоков heartbeat 319–577 мс, UDP 12/12.
Диагностические счётчики creditWaits=0: исчерпание согласованного окна не наблюдалось
в этих фазах; ожидание sendBuffer есть, но увеличение его уже не давало выигрыша.
Ограничения продукта сохранены; деление файлов должно делать само приложение
с учётом поддержки сервера. Один произвольный TCP/TLS поток туннель не превращает
в несколько независимых загрузок. Оба запуска завершили свои TCP/UDP процессы.
