# Phone Exit: правила проекта

## Цель и подтверждённые факты

Создать собственный клиент для Windows и приложение Android, чтобы приложения
на ПК могли выходить в интернет через Wi-Fi удалённого телефона без настройки
роутеров. Язык интерфейса и документации — русский.

11 октября 2026 браузерный тест `webrtc-probe/` подтвердил прямой WebRTC
DataChannel между ПК и удалённым Android: UDP, prflx ↔ srflx, ответы 223–233 мс.
Это подтверждает возможность связи в этих сетях, а не готовность VPN.

Хостинг demochko.com: PHP передаёт только offer/answer/ICE через HTTPS.
WebSocket на проверенных маршрутах не работает; изменения PHP disable_functions
не решают ограничения Apache/Passenger. WHM и существующий сайт не менять.

## Обязательные режимы Windows

Пользователь запросил два режима: весь трафик ПК через телефон и только трафик
выбранных приложений/игр (остальные выходят через обычное подключение ПК).
Выбор по исполняемому файлу/процессу; учитывать дочерние процессы и отдельные
процессы игры и лаунчера. Поддержка UDP обязательна для завершения продукта.
Системный TUN и маршрутизация по процессам нужны сверх первого SOCKS-этапа.
Не показывать режимы как работающие, пока реализован только TCP SOCKS.
Согласованная политика: при потере телефона выбранный для туннеля трафик
блокируется, остальной в выборочном режиме продолжает обычную работу.
Не применять маршруты, драйверы и права администратора без конкретной
необходимости и понятного пользователю действия включения режима.

## Архитектура и этапы

Код продукта размещать в `phone-exit/`, старые диагностические проекты сохранять.

Первый рабочий этап: локальный SOCKS5 CONNECT на 127.0.0.1 ПК → надёжный
WebRTC DataChannel → TCP-сокеты Android, привязанные к Wi-Fi Network.
DNS имён назначений выполняется на телефоне через тот же Wi-Fi.
PHP не передаёт пользовательский трафик. TURN по умолчанию отсутствует.
При невозможности прямой связи сообщать ошибку, не включать сторонний relay.

SOCKS5 — первый этап, не системный VPN. Последующий этап: клиентский TUN
на Windows, маршрутизация и DNS; UDP/QUIC требуют отдельной реализации.
Не обещать работу всех приложений, UDP или системного трафика на первом этапе.
На Android выход в интернет реализуется обычными сокетами; VpnService для
телефона как exit node сам по себе не нужен.

## Ограничения и безопасность

- Ключ сопряжения: минимум 256 случайных бит; не хранить в репозитории и логах.
- Использовать HTTPS с обычной проверкой сертификатов и DTLS WebRTC.
- Не открывать SOCKS на внешнем интерфейсе, не менять firewall и защиту ОС.
- Телефон начинает обслуживание только после явного действия пользователя;
  показывать уведомление foreground service и кнопку остановки.
- Wi-Fi обязателен: при его исчезновении остановить выход, без перехода на LTE.
- Ограничивать число потоков, размер кадров, очереди, время открытия сокетов.
- Поддерживать backpressure и закрытие потоков в обе стороны; при потере канала
  закрывать все сокеты. Не оставлять необслуживаемые фоновые процессы.
- Отклонять loopback/private/link-local/multicast адреса назначения на телефоне,
  включая DNS, возвращающий такие адреса; доступ к LAN не входит в первую версию.
- Не собирать содержимое трафика, адреса посещённых сайтов и постоянную телеметрию.
- Не менять существующие файлы сайта. Деплой продукта — в отдельный каталог.
- Не распространять APK и не публиковать внешние изменения без проверки сборки.

## Работа и проверка

Использовать закреплённые версии библиотек и lock-файлы. Не коммитить SDK,
node_modules, сборки, ключи и данные комнат. Секреты задавать во время запуска.
Документировать протокол между платформами до расхождений в реализациях.

Проверки первого этапа: SOCKS handshake/CONNECT и отклонение UDP/BIND;
несколько параллельных TCP-потоков; бинарные данные; DNS на телефоне;
таймауты, half-close, переполнение, потеря Wi-Fi/канала; изоляция комнат PHP.
Локальный интеграционный тест должен проходить через настоящий WebRTC.
Перед заявлением «работает на телефоне» собрать APK и проверить с удалённым
Android: HTTPS-запрос через SOCKS, внешний IP и выключение Wi-Fi.

Если SDK или устройство недоступны, явно фиксировать, что собрано и проверено,
а что ещё требует устройства. Не выдавать заглушки за готовый VPN.
Обновлять README и состояние проекта по фактическим результатам.

Не создавать подагентов без прямой просьбы пользователя.

## Персональная автоматика, 11 октября 2026

Пользователь явно выбрал персональный APK без ввода кодов. `android/build-personal.ps1`
создаёт/читает DPAPI CurrentUser `%LOCALAPPDATA%/PhoneExit/account.bin` и собирает
`phone-exit/PhoneExit-personal.apk`. APK содержит capability добавления в личный
список; передавать только на свои телефоны, не публиковать. Asset генерируется
в игнорируемой `.tools/personal-assets`, ключи не выводятся. Закрытый ключ ПК
остаётся только в DPAPI-файле. Не заменять account.bin при обычной пересборке:
он связывает этот профиль ПК и уже выданные APK. Экспорт/перенос аккаунта пока нет.

При первом открытии персонального APK создаётся уникальный id/ключ телефона,
зашифрованный Keystore, и включается явный foreground-доступ с уведомлением.
В ручном коде/копировании больше нет необходимости; поле кода скрыто на обеих
платформах персонального режима. Телефон отправляет зашифрованную регистрацию
в общую личную комнату: ECDH P-256 → SHA256 → AES-256-GCM, AAD version label,
одноразовый ephemeral key/IV. ПК сам добавляет новые устройства и страны в список.
Комната регистрации имеет HMAC ключ от feedToken с отдельной меткой протокола,
ротация 5 мин. PHP не менялся; хранит ограниченные ciphertext-сообщения.
Персональный APK даёт его обладателю возможность добавлять устройства в этот список.

Foreground-служба хранит enabled-флаг, START_STICKY, BOOT_COMPLETED/package-replaced
receiver, ожидает Wi-Fi без таймаута. Сетевые callbacks плюс проверка сети каждые
5 с восстанавливают агента после смены сети. HTTP ошибки повторяются с backoff
до 30 с; активные TCP закрываются при потере Wi-Fi, LTE не используется.
Stop выключает enabled, поэтому самовключения после явной остановки нет.
ПК обновляет stale-статусы даже при зависшем HTTP-запросе. В ПК-системном режиме
автоподключения сокетов пока нет: после возврата телефона выбирают «Подключить».

Реальный тест `pc/test-personal-usb.ps1`: ПК начинает с пустого списка и только
ключом аккаунта; vivo регистрируется из APK без кода, страна UA; три HTTPS через
WebRTC; удерживаемый TCP закрывается при выключении Wi-Fi; запись становится
offline; Android-служба остаётся ждать; Wi-Fi включён снова, телефон автоматически
регистрируется, HTTPS снова проходит без открытия Activity и передачи кода.
APK установлен на vivo. После теста Wi-Fi включён и автоматический выход активен;
клиент ПК открыт в ожидании, SOCKS создаётся только после подключения.
Запуск после настоящей перезагрузки и убийства процесса системой не проверялся;
Android force-stop требует открытия приложения, а OEM battery policy может мешать.
Сборка/lint: 0 ошибок, 2 предупреждения (backup compatibility, ресурс текста).
Локальные тесты: автообнаружение без прежних ключей, несколько стран, неверный
аккаунт/подмена/stale, блокировка удалённого id, старые WebRTC/TCP тесты пройдены.

## Windows EXE запуск

Phone Exit.exe — небольшой WinForms launcher с иконкой, собранный из pc/launcher.cs
командой pc/build-launcher.ps1 (системный .NET Framework csc). Запускает desktop.ps1
из каталога EXE независимо от текущей папки; EXE не является автономным установщиком,
лежит рядом с pc и остальными файлами. install-shortcuts.ps1 теперь указывает на EXE.
Desktop использует mutex текущего пользователя: повторный запуск восстанавливает и
показывает существующее окно. SelfTest/VpnTest не используют mutex. Проверены EXE
из C:/Windows и повторный запуск: остаётся один GUI. Сохранённые телефоны отображаются
сразу до сетевых запросов как offline, затем обновляется доступность; ключи не выводятся.

регистра G:/g: не обнаружила ошибки. Добавлен отступ 12 логических px между пингом и
режимом, связанные элементы сдвинуты; layout/smoke прошли.
